# Changelog

All notable changes are listed here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- Surrogates are no longer pickled: a surrogate is saved as its training samples (HDF5) with its settings, and trained again where it is used, in a fraction of a second, with the same result. Antivirus software such as Microsoft Defender quarantined the pickles, which can run code when they are loaded. The generated scripts build surrogates with `create_surrogate` from the samples; the demos save their samples the same way. Surrogates and scripts of earlier versions still work.
- A value typed on an input is kept when the component is read again, even if the discipline has its own default value.
- Default values of more than 1,000 elements are no longer copied into the project: their ports keep their shape and type.
- Every name SymPy reads as a function or a constant (`gamma`, `beta`, `test`…), not only `S`, `N`, `E`, `I`, `O` and `Q`, is refused as a variable of a formula.
- A modern interface, close to n8n:
  - a top bar with the application menu, the state of the project and a prominent Run button;
  - an icon rail opening the panels, which float as rounded cards;
  - cards with colored icons on a dotted canvas, with run states (a pulsing ring, then a check);
  - toasts when a project is saved, a model is valid or a run ends;
  - the Inter font.
- The native menu bar is replaced by the menu of the top bar. The bottom panel is closed by default.
- Drivers have a card with the icon of their kind, like the other nodes, and can be steps of a sequence. Dragging from a driver onto a node puts the node under its control.

### Added

- The restoration of feasibility of the large-scale optimizer is up to 20 times cheaper: its last iterations solve their subproblems with the constraints tightened by a small margin rather than to the finest tolerance, and the dual solver keeps more memory (a restoration iteration of a bracket of 10⁴ elements took 8 minutes).
- The large-scale optimizer restores feasibility before the end of GEMSEO's budget of evaluations, not only before its own `max_iter` iterations: GCMMA makes several evaluations per iteration, and a run ended with its converged iterates just above the constraint limits and an early feasible point.
- The Claude copilot anticipates where the optimization is heading and steers it there (`steer`): it sees the trend of the design and the design it leads to, and extrapolates the trend, transforms a described design or sets variables; the large-scale optimizer goes on from the steered design at its next iteration, its state kept, without waiting for Claude. The first call comes after the first iteration, to judge whether the run started from a viable point.
- The Claude copilot follows the large-scale optimizer more closely and stops it sooner: a call every 10 outer iterations, or at the first one 10 seconds after its last answer, and a `plateau` event when the objective improves by less than 0.5 % over 10 of them, for Claude to stop the run or restart it rather than let it spend iterations for nothing. A decision on these algorithms expires after 10 outer iterations, not 50 evaluations; a slightly infeasible run that still progresses is no longer taken for stuck. The models are chosen in lists in the preferences (Claude Opus 5.5, Sonnet 5, Haiku 4.5, Opus 5, Fable 5.1) with the effort of the calls: Claude Opus 5.5 at a low effort by default, for both roles.
- The Claude copilot reads the design of a model that describes its physics, as an engineer would: the physical problem in words, maps of the density and of the stresses with the supports, loads and geometric features marked, and physical indicators — whether the material carries the loads to the supports, members thinner than the filter allows, gray and dead material, stress hot spots and the feature they sit at, where the constraints cost most. When the run is stuck, Claude explains it physically and can restart it from a transformed design (a region filled or emptied, a corner rounded, a bar closing a load path); the next calls compare the design before and after, and the report ends with the maps of the final design and of each restart. The stress-constrained topology benchmark describes its physics.
- A large-scale optimizer, `gemseo-lso` (`plugins/gemseo_lso`, specified in docs/LARGE_SCALE_OPTIMIZER_SPEC.md), for problems of 10⁵ to 10⁶ variables and constraints: its core, MMA and GCMMA written from Svanberg's papers in NumPy and SciPy, running one iteration at a time, its state saved in HDF5 and resumed exactly, its settings changed between two iterations without a restart. Each iteration asks only for the gradients of the constraints close to activity, checks the step against all the constraint values and repairs it when a screened-out constraint would be violated; gradients far from activity can be reused while they are young; sparse gradients and a few equality constraints are supported. The gradients are kept in float64 by default (float32 halves their memory); the optimizer stops at a KKT residual of 1e-3 by default.
- The large-scale optimizer in GEMSEO and in the application: the algorithms `LSO_MMA` and `LSO_GCMMA`, listed with the others when `gemseo-lso` is installed in the Python of the runs, with their explanation. The gradients of the constraints come from GEMSEO in full, or row by row from the disciplines that offer them (only the rows of the working set: a scenario of 10⁵ variables and constraints converges in 8 seconds without a whole Jacobian ever computed). The driver editor offers the colored Jacobians of these algorithms, unchecked by default, with the function of a project file giving the sparsity pattern; the generated script passes it, and a script read back keeps it.
- Colored Jacobians in the large-scale optimizer, optional and off by default: when the model gives the sparsity pattern of its constraints, the whole Jacobian costs a few tens of directional derivatives (its tangent mode, or finite differences) instead of one gradient per constraint. Several colorings measure each entry and estimate its error; the exact gradients of the constraints near activity are still computed (the hybrid mode), so that the optimum is the model's. `probe_sparsity` measures how far a model is from its pattern.
- The large-scale optimizer stays within its constraints: a run that settles, or nears its maximum of iterations, outside them brings itself back (smaller steps, GCMMA, a finer subproblem), and the result is the best feasible point met. On stress-constrained topology optimization, the designs no longer end 0.3 to 0.9 % above the stress limit.
- The Claude copilot pilots the large-scale optimizer live: it reads the report of each iteration (working set, gradients asked for, repairs, KKT residual…), its changes of settings and its switch between MMA and GCMMA apply at the next iteration without restarting, and six detectors of its own call it (repairs at each iteration, a churning working set, narrowed asymptotes, many inner iterations, stale gradients, a budget of gradients running out). Constraints of many components are summarized for Claude, whatever their size (2,100 tokens for 10⁶ components), and read by slices. The Copilot view charts the working set and the gradients per iteration. A stopped run of the optimizer can be saved and resumed, and a budget of gradients set.
- The large-scale optimizer in GEMSEO no longer stops early: GEMSEO's `ftol_rel` and `xtol_rel` compared its last evaluations, which GCMMA's inner iterations make close to each other; they now apply to the iterations of the optimizer. Its KKT residual is relative to all the terms of the problem, not to the gradient of the objective alone (a volume under stress constraints read 10 to 10⁶). Its subproblem follows the scale of the objective and of each constraint: the units of the problem no longer change the run, nor the constraint gradients it asks for. Its rows are kept in float64 by default: float32 rounded the subproblem too much for the restoration of feasibility.
- The large-scale optimizer on problems of the literature (trusses of 10, 25 and 72 bars, Svanberg's beam, Hock–Schittkowski 71, 100 and 113; `plugins/gemseo_lso/benchmarks/run_literature.py`): it reaches the published optima. They showed silent failures of the dual solvers, now detected and solved again, and a better automatic choice of the dual solver for many variables and few constraints.
- The large-scale optimizer can go through the constraints on its way to the optimum (`descent_iterations`, off by default): from a neutral start, a descent with soft constraints towards the lightest design (the fully stressed one, for a structure), then the restoration of feasibility and the normal iterations.
- The README and the user guide show the application: a tour of the interface, the bi-level wing sizing in detail (its levels, N2, XDSM, driver editor, a run and its results), and the Copilot tab and preferences, with screenshots in `docs/images/`.
- Claude can test whether a run is in a local optimum: the reports of the large-scale optimizer list the variables at a bound and what leaving each would cost, a `frozen` event fires when the run settles with variables at a bound, and the prompt (version 6) asks Claude to lift the cheapest ones with a steering and see whether they come back.
- A benchmark of stress-constrained topology optimization for the large-scale optimizer (`plugins/gemseo_lso/benchmarks/run_topology.py`): an L-shaped bracket of 10⁴ to 10⁵ plane-stress elements, one von Mises constraint per element, gradients by adjoint.
- First part of the Claude copilot (`plugins/gemseo_claude_pilot`, specified in docs/CLAUDE_PILOT_SPEC.md): the decisions Claude may take and the limits they must respect, the detection of stagnation, infeasibility, divergence, failed evaluations, oscillation and bounds, the context sent to Claude with its three data levels (full, without code, anonymized), and a fake backend for the tests. `ClaudePilot` runs an optimization in segments: Claude is called on its triggers without blocking the optimizer, and a decision that passes the checks (new settings, narrower bounds, another algorithm, stop) starts a new segment from the best point, without evaluating any point again; every call and decision is written to a journal. Claude is reached through your own Claude Code and subscription by default (none of its built-in tools, no settings, only the pilot's tools), or with an API key (`GEMSEO_CLAUDE_PILOT_BACKEND=api_key`, the key in the environment or the OS keyring); a budget per run bounds the calls and tokens, and the cost with a key is estimated. An optimization driver can be piloted: its generated script runs the scenario through `ClaudePilot` in a few readable lines, and is read back into the driver; a run started from the application reports what Claude says and does, and its proposals can be accepted or rejected (Advisor mode). The journal of the copilot is in the run folder. In the application: the Claude copilot section of the preferences (Claude Code or API key, with a check, the key in the keyring, the models, the defaults), the Copilot tab of an optimization with a consent before anything is sent, and the Copilot view of the results with Accept and Reject, the mode, the usage and the segments, marked on the History charts. Talking with the copilot: *Review with Claude* before a run, questions during or after a run, and an analysis of each piloted run written by Claude at its end, offered in the report. DOEs, bi-level studies and surrogates: a DOE can be piloted, Claude placing half of the samples (possibly in a sub-region); Claude can retune the sub-optimizations of a bi-level study between two system iterations; it is told how each surrogate was trained and how well it fits.
- Projects saved as GEMSEO scripts: Save writes a readable, runnable script and nothing else; your own code in the script is kept, and opening a script reads it, with its runs and surrogates found again next to it. Projects of older versions (`.gpb.json`) still open and are saved as scripts. The examples are scripts. Runs, surrogates, autosave and lock are kept in the data folder of the application, out of sight: only the script is next to it. A script moved or renamed outside the application finds them again, by its content or its model; when several could match, you choose. Scripts are checked before they are read: studies for GEMSEO 5 or earlier and other programs are refused, with the lines to change, and never run; the worker requires GEMSEO 6. Studies written in several files are read with every kind of component, including surrogates pickled by hand and the settings of nested optimizations, and their modules are read again when they change (example: examples/demoBiLevel). The Library lists the examples as demos, shipped in the package: a click opens a copy of one. New demo: the wing sizing in bi-level, optimized on surrogates and checked on the normal models they replace; and its variant with 100,000 variables, converging in about 15 iterations on exact gradients and post-optimal sensitivities.
- Open GEMSEO scripts written by hand: Open project… reads a `.py` file into a project, running it until its study would start.
- Create an example: a working example of each kind of component (Analytic, Python function, Python class, executable wrapper, surrogate), written where you choose, from the inspector of a component not set up yet.
- NumPy arrays in the Python classes written from the inspector: each input has a shape, a type (float, int, complex) and a default value filling it; the classes use GEMSEO's simple grammar, which accepts matrices and checks data 30 times faster than a JSON grammar.
- Fast mode of a driver (Execution tab): GEMSEO does not check the data the disciplines exchange.
- Python classes written from the inspector: New Python file… writes a GEMSEO discipline class with its inputs and outputs, a table edits them in the class, Open in editor opens the file in your code editor (a new Code editor preference), and saving the file updates the component.
- Algorithms explained: what each optimization algorithm, sampling method and formulation does, when to use it and what it costs; a comparison of all of them; the algorithm suggested for an optimization problem, and why; tips in the design variables, objectives and constraints tabs.
- Guidance: the steps to set up a driver at the top of its editor, with a button for each; pickers say why they offer nothing; the formulas of an Analytic component have examples, completion (Tab), the list of functions and operators, and the inputs and outputs they define.
- Response surface in the results: a response over two design variables predicted by Kriging, a neural network, radial basis functions or a quadratic polynomial, in 2D or 3D, with the constraint boundaries and the infeasible regions.
- Results of large runs: a filter shared by the views keeps the design variables the response is most sensitive to, those with the largest gradients or those at a bound, and the active and violated constraints; the runner also saves the results in binary (`dataset.npy`), read 40 times faster.
- Derivatives: the origin of the derivatives of each component on its card (exact, approximated, none), Check derivatives on any node (GEMSEO's derivatives against finite differences, through the whole process for a driver), and a Gradients view in the results.
- Developer tools of the page: F12, Tools › Developer tools, or a right click where no other menu opens.
- NLopt optimization algorithms (MMA, SLSQP, COBYLA, BOBYQA, NEWUOA, BFGS), through the `nlopt` package.
- Start and end of the workflow: every level shows its inputs (whose values are typed once, for every node using them) and its results (the outputs no node uses, and the ones chosen).
- Execution arrows: the nodes of a chain are numbered and linked by arrows, and a chain is reordered by dragging an arrow from a node to the one that must run next. Parallel blocks show a fork and a join. A node running before the results it uses is an error. In a group run automatically, drawing an arrow makes it a chain, so an optimizer can be a step of a sequence.
- Optimization sequence example: material data, then the optimization of a beam, then its cost.
- Wing sizing example: three coupled analytic disciplines under an optimizer.
- Beam chain example: an assembly run as a chain, in order, under a DOE.

## [0.1.0]

First public release.

### Added

- Derivatives: the origin of the derivatives of each component on its card (exact, approximated, none), Check derivatives on any node (GEMSEO's derivatives against finite differences, through the whole process for a driver), and a Gradients view in the results.
- Start and end of the workflow: every level shows its inputs (whose values are typed once, for every node using them) and its results (the outputs no node uses, and the ones chosen).
- Workflow canvas (SVG, d3): components as cards, one link per pair of nodes, a panel showing the variables of both sides of a link, hierarchical navigation, containers expanded in place, minimap, search, auto-layout (elkjs in a Web Worker), undo and redo.
- Components: analytic expressions, Python functions, GEMSEO discipline classes, executable wrappers of external codes, surrogate models; catalog folders scanned in a subprocess.
- Linking by name and by explicit links, isolated namespaces, units checked and converted with pint, N-D arrays flattened when needed.
- Assemblies (auto, chain, parallel, MDA) and drivers: MDA, DOE, optimization (MDF, IDF, DisciplinaryOpt, BiLevel), parametric study, nested drivers with their interface.
- Continuous validation with quick fixes, and a dry run of the generated script.
- Readable GEMSEO scripts exported from a model or a driver.
- Runs in separate processes with live progress, stop and kill; run history kept with each project.
- Results: summary, history, table, scatter matrix, XY plot, parallel coordinates, parametric views, run comparison, GEMSEO post-processings.
- N2 and XDSM views.
- Graphical editor of executable wrappers, with sample files, suggested output rules and test runs; reusable wrapper descriptors.
- Surrogate wizard: GEMSEO regression models, cross-validated quality, predicted-vs-observed charts.
- Exports: images (SVG, PNG) of every view, project report (HTML, PDF).
- Autosave and recovery, read-only opening of projects open elsewhere, atomic file writes, non-blocking dialogs for unexpected errors.
- Benchmarks of the performance targets on a 2,000-component, 50,000-variable model.
