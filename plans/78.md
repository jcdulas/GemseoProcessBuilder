# 78 — Resuming a run from its caches

Status: Done (the acceptance by hand is to do)
Depends on: 19, 77
SPEC: § 3.4, 6.4, 8.8, 11.1, 11.4, 12.1; [SIZING_LOOP_EVOLUTIONS.md](../docs/SIZING_LOOP_EVOLUTIONS.md) § 4 (GPB-E3)

## Goal

A run that failed, was stopped or was killed is resumed from the Runs panel: a new run executes the same script, and the file caches of its disciplines (plan 77) serve the evaluations already done. A crash after 40 of 50 sized architectures costs 10 sizings, not 50. A killed run keeps the history of its evaluations when its driver saves it after each one. Milestone M4 of the sizing loop (ECOSYSTEM-EVOLUTIONS.md § 6).

## Scope

In:
- **Resume** in the Runs panel for a run *failed*, *stopped* or *killed*; bridge method `run.resume(runId)`;
- the run manager: a new run folder with copies of the snapshot, the script and the mapping of the run resumed; no validation, no generation, no dry run; the runner executes that script (SPEC § 11.1);
- `resumed_from` in `run.json`; the console reports the cache entries reused (from GEMSEO's "Found N entries in the cache file");
- the Execution tab: **Save the history after each evaluation** (off by default), written as `set_optimization_history_backup(..., at_each_function_call=True)` to the `history.h5` beside the script, read back by the script reader; the Results of a killed run read that history;
- a DOE resumed draws the same samples (GEMSEO's seeder starts from its default seed in each process, or from the seed the script sets): checked by a test.

Out:
- a run resumed after its components changed: the fingerprints of plan 77 warn;
- the exact resume of the large-scale optimizer (`save_state`, `resume_from`), unchanged.

## Implementation notes

- Built in f264224 (2026-10-13), after plan 77 (ac97703); the plan was ticked by the records pass of 2026-10-27 (lane H), from that commit. The user guide gained its paragraph on Resume in 0aec6ef (plan 80), the changelog its entry in the records pass.
- Files as built: the Results of a killed run are written by `results/recovery.py` (with `results/reader.py` and `results/models.py`), not `results/store.py`; the states of the Runs panel action are in `static/js/lib/run_resume.js` (`canResume`, tested by `tests/js/run_resume.test.js`).
- Resume: `RunManager.resume` (`RESUMABLE`: failed, stopped, killed; `RUN_FILES`: the snapshot, the script and the mapping, all required), bridge method `run.resume(runId)`; `resumed_from` in `run.json`. The console line of the entries reused is GEMSEO's own log (`Found N entries in the cache file`), shown by the console: no line of the application (SPEC § 11.1).
- History after each evaluation: `Execution.history_each_evaluation`, a driver run on its own; written as `set_optimization_history_backup(Path(__file__).parent / "history.h5", at_each_function_call=True, erase=True)` in `build_scenario()` (golden `rosenbrock_doe_backup.py`), read back by the script reader without writing the file. The Results of a killed run are written from `history.h5` by the worker the first time they are opened (`dataset.csv`, `dataset.npy` and the variables of `run.json`).
- Later: plan 81 (ccc6886, 2026-10-22) puts a resumed run beside the run it resumes when its driver has a working folder.
- Not done: the acceptance by hand in the window (a DOE of a slow component with a file cache, killed halfway, then resumed). The in-process test shows a DOE crashed after 3 samples served by its file on the second run, with the same samples.
