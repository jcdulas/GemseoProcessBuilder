# 78 — Resuming a run from its caches

Status: To do
Depends on: 19, 77
SPEC: § 3.4, 6.4, 8.8, 11.1, 11.4, 12.1; [SIZING_LOOP_EVOLUTIONS.md](../docs/SIZING_LOOP_EVOLUTIONS.md) § 4 (GPB-E3)

## Goal

A run that failed, was stopped or was killed is resumed from the Runs panel: a new run executes the same script, and the file caches of its disciplines (plan 77) serve the evaluations already done. A crash after 40 of 50 sized architectures costs 10 sizings, not 50. A killed run keeps the history of its evaluations when its driver saves it after each one. Milestone M4 of the sizing loop (ECOSYSTEM-EVOLUTIONS.md § 6).

## Scope

In:
- **Resume** in the Runs panel for a run *failed*, *stopped* or *killed*; bridge method `run.resume(runId)`;
- the run manager: a new run folder with copies of the snapshot, the script and the mapping of the run resumed; no validation, no generation, no dry run; the runner executes that script (SPEC § 11.1);
- `resumed_from` in `run.json`; the console reports the cache entries reused (from GEMSEO's "Found N entries in the cache file");
- the Execution tab: **Save the history after each evaluation** (off by default), written as `set_optimization_history_backup(..., at_each_function_call=True)` to the `history.h5` beside the script, read back by the script reader; the Results of a killed run read that history;
- a DOE resumed draws the same samples (GEMSEO's seeder starts from its default seed in each process, or from the seed the script sets): checked by a test.

Out:
- a run resumed after its components changed: the fingerprints of plan 77 warn;
- the exact resume of the large-scale optimizer (`save_state`, `resume_from`), unchanged.
