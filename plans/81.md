# 81 — The working folder of a driver

Status: Done
Depends on: 19, 77, 78
SPEC: § 6.4, 8.7, 11.1, 12.1, 17 (open point 13)

## Goal

The Execution tab of a driver shows a **Working folder** that was stored but read by nothing (open point 13). The owner decided on 2026-10-19 that it is the study's run folder: the runs of the driver, their outputs and logs, are written there, and the file caches of its disciplines default to its `cache/`.

## Scope

In:
- `core/drivers.py`: `working_folder(driver, project_folder)` (absolute, or relative to the folder of the project file; `None` when empty) and `nearest_working_folder(project, node_id, project_folder)`;
- `results/store.py`: `runs_folder_of(target)`, the runs folder of a target; the orphans looked for under the working folders of the drivers too;
- `app/run_manager.py`: a run of a driver with a working folder in `<working folder>/<run_id>/`, created with its parents (a folder that cannot be created is a `RunError` with its reason); a resumed run beside the run it resumes;
- `core/caches.py`, `app/api_cache.py`, `static/js/panels/inspector_cache.js`: `cache.defaultFile(id)` gives `<working folder>/cache/<project name>.h5` for a node inside a driver with a working folder;
- the hint of the field in `panels/driver_editor/settings_tabs.js`.

Out:
- a path of the working folder in the generated script: the runner's current folder is already the run folder (§ 10.3);
- moving the runs or the caches when the working folder changes: a run keeps its folder, a cache file its path.

## Implementation notes

- Each run keeps its own `<run_id>/` folder under the working folder (not the working folder itself), so that two runs never overwrite each other and deleting a run never deletes the user's folder; the owner's "run folder" is read as the folder of the study's runs.
- The working folder of a driver nested in the target is not read for the folder of the run, only for the default file of the caches of the disciplines inside it.
