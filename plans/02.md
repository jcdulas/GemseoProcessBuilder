# 02 — QWebChannel bridge

Status: Not started
Depends on: 01
SPEC: § 3.3, § 3.4

## Goal

Provide the single communication path between JS and Python: promise-based calls from JS to Python handlers, events from Python to JS, a uniform error model, and background execution for long operations.

## Scope

In:
- `Bridge(QObject)` with the `call` slot and the `reply` / `event` signals.
- Method registry and dispatcher on the Python side.
- `bridge.js`: `api.call()`, `api.on(type, handler)`, timeouts.
- Error model and error codes.
- Long operations run on a `QThreadPool`, result sent back on the Qt thread.
- A few built-in methods: `app.ping`, `app.version`, `app.echo` (for tests and the dev console).

Out:
- Business methods (added by each later plan).

## Deliverables

```
gemseo_process_builder/app/bridge.py        # Bridge, MethodRegistry, BridgeError
gemseo_process_builder/app/api_app.py       # app.* methods
gemseo_process_builder/static/js/bridge.js  # connect(), api.call(), api.on()
gemseo_process_builder/static/js/lib/rpc.js # pure: pending-call table, timeouts, message parsing
tests/python/test_bridge.py
tests/js/rpc.test.js
```

## Design

- Request: `{ "id": str, "method": str, "params": object }`. Reply: `{ "id", "ok": true, "result" }` or `{ "id", "ok": false, "error": { "code", "message", "details" } }`. Event: `{ "type": str, "payload": object }`. All payloads are JSON strings on the Qt side.
- Handlers are registered with a decorator: `@registry.method("project.open")` or `@registry.method("catalog.refresh", background=True)`. Handlers receive validated params (a Pydantic model per method, declared by type annotation) and return a JSON-serializable value.
- Error codes: `invalid_request`, `unknown_method`, `invalid_params` (Pydantic errors in `details`), `not_found`, `conflict`, `worker_unavailable`, `internal` (traceback in `details` only in `--dev`).
- Background handlers run in `QThreadPool.globalInstance()`; completion is marshalled to the Qt thread with a queued signal before emitting `reply`.
- `bridge.emit_event(type, payload)` is the only way Python pushes events.
- JS: `await connect()` creates the `QWebChannel` and resolves when `bridge` is available. `api.call(method, params, { timeout = 30000 })` returns a Promise rejected with an `ApiError` (code, message, details) on error or timeout. `api.on(type, fn)` returns an unsubscribe function.

## Steps

- [ ] Implement `MethodRegistry` (register, lookup, params validation) independent of Qt, so it can be tested without a web view.
- [ ] Implement `Bridge` on top of it; attach it to the page's `QWebChannel` under the name `bridge` in `MainWindow`.
- [ ] Implement `lib/rpc.js` (pure) and `bridge.js` (uses `window.QWebChannel` and `qt.webChannelTransport`).
- [ ] Load `vendor/qwebchannel.js` in `index.html`.
- [ ] Add `app.ping`, `app.version`, `app.echo`; make `main.js` show the version returned by Python in the page.
- [ ] Log every call (method, duration, ok/error) at DEBUG level.

## Tests

- `test_bridge.py`: dispatch of a sync method; unknown method; invalid params; handler raising → `internal`; background method delivering its reply (use a `QEventLoop` with a 500 ms guard); event emission payload format. No web view needed: connect to the `reply`/`event` signals directly.
- `rpc.test.js`: id generation, resolving and rejecting pending calls, timeout, malformed reply, event dispatch and unsubscribe.

## Acceptance criteria

- The page displays the version obtained through `api.call("app.version")`.
- `python tools/check.py` passes.
