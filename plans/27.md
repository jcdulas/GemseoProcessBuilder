# 27 — Units and variable types

Status: Done
Depends on: 14
SPEC: § 5.5, § 5.6, § 9.1 (unit and type rules)

## Goal

Handle physical units (checks and automatic conversions) and the full set of variable types (N-D arrays, strings, paths) consistently across the resolver, validation, the canvas and codegen.

## Scope

In:
- Units with **pint** in the UI process (pint is pure Python, no GEMSEO):
  - parsing and normalization of unit strings; invalid unit → error on the port;
  - coupling check: incompatible dimensions → error; compatible but different → warning + conversion; missing on one side → info;
  - per-link "Disable conversion" option (stored on the link, or on the coupling for implicit ones).
- Unit sources: user entry in the Variables table (with autocompletion of common units), `@component(units=…)`, grammar metadata when available (checked in the worker during introspection).
- Canvas: link compatibility feedback now includes units; link tooltip shows the conversion (`mm → m, × 0.001`); converted links get a small marker.
- Codegen: insert a conversion discipline per converted coupling (a `LinearDiscipline` or an `AnalyticDiscipline` for affine conversions such as °C → K), named after the variable (`convert_thickness_mm_to_m`), with a comment; the consumer is remapped to the converted name.
- Variable types:
  - N-D arrays: warning when used as MDA coupling or design variable; optional automatic flattening/reshaping (a user-accepted flag on the port), generated as explicit `reshape` in small wrapper disciplines with comments;
  - `str` / `path`: error when used as design variable, objective, constraint or MDA coupling;
  - dtype mismatch rules extended (int → float allowed with info, float → int error).
- Validation rules for all of the above, with quick fixes ("Enable conversion", "Accept flattening").

Out:
- Unit conversion inside executable wrappers (plan 28 reads units from descriptors, conversions still happen here).

## Design

- Unit logic lives in Python only; the resolver output carries unit compatibility per coupling so JS never needs pint.
- pint's registry is created once per process (it is slow to create); tests reuse a module-level registry created at collection time.

## Implementation notes

- `core/units.py` (pint, UI process):
  - The registry is created once, on first use (`registry()` is cached), and conftest warms it up.
  - `check(source, target)` returns `same`, `convert` (with `factor`, `offset` and a message like `mm → m, × 0.001` or `degC → K, + 273.15`, affine for temperatures), `incompatible`, `missing` or `invalid`; it is cached too.
  - `is_valid`, `parse`, and `suggestions` (a list of common units).
  - Ruff allows the `×` and `−` signs of these messages (`allowed-confusables`).
- Model:
  - `Port.convert_units` holds the option for couplings by name; explicit links already had `Link.convert_units`.
  - `Port.flatten` accepts to exchange an N-D array as a 1-D vector.
  - Commands `setPortOptions` (unit, convert_units, flatten) and `setLinkOptions` are both in the undo round trip test.
- Resolver: each coupled variable of `level_view` edges carries `unit` (Python's check) and `converted`, so JS never needs pint. The producer and consumer ports are looked up inside containers too.
- Rules (`core/rules/units_types.py`):
  - `invalid_unit` (error), `incompatible_units` (error), `unit_conversion` (warning), `unit_not_converted` (warning, quick fix "enable_conversion", which sets the link option or the input option), `unit_missing` (info);
  - `int_to_float` (info), `text_mda_coupling` (error);
  - `nd_mda_coupling` (warning on the producer) and `nd_design_variable` (warning on the input), both with the quick fix "accept_flattening".
  - Loop variables are those on edges within a strongly connected component of a level.
- Codegen (`codegen/conversions.py`, planned in `generate()` as `context.exchanges`):
  - A conversion is a `LinearCombination` (coefficient, `offset` when affine, `input_size` for vectors) named `convert_<name>_<unit>_to_<unit>`. It sits right after the producer with a comment, and the consumer reads `<name>_<unit>` through its `RemappingDiscipline`.
  - Flattened N-D arrays: a `Reshape` class is written once into the script. The component, remapped to `<name>_<rows>x<cols>` or `<name>_<component>` names, is wrapped in `MDOChain([reshaped inputs, component, flattened outputs], name="<Name>_vectors")`.
  - The wrapper approximates its derivatives on the vectors, because GEMSEO's finite differences cannot perturb 2-D inputs; this was checked by hand. Reshaped inputs start from the component's default values.
  - A plain chain of flatten and reshape adapters would have left the N-D variables inside the MDA loop, hence the wrapper.
- Checked in GEMSEO 6.3: MDAs fail with 2-D couplings and design spaces refuse 2-D inputs, and both work once wrapped. GEMSEO's grammars carry no unit metadata, so units come from the Variables table and from `@component(units=…)`, which introspection already read.
- Page:
  - `unitCompatibility` and `conversionNotes` (`lib/link_compat.js`). While drawing a link, `units.check` is asked once per unit pair (cached), and the hint shows the conversion, or refuses incompatible units.
  - Converted links are dash-dotted, and their tooltip lists the conversions. The link inspector has a "Convert (…)" checkbox per variable.
  - Variables table: unit autocompletion from a `<datalist>` (`components/unit_input.js`, `units.suggestions`; `EditableTable` gains a `datalist` column option) and a "1-D" checkbox for N-D ports.
- Tests:
  - `test_units.py`, `test_rules_units_types.py` (one triggering and one clean case per rule, quick fixes);
  - `test_conversions.py`: the golden model gives stress = 1000 × 0.001 + 293.15, disabled conversions are left out, 2×2 matrices in an MDA loop converge to 4/3, and a 2×2 design variable reaches 0.3;
  - JS tests of the unit feedback.
- Smoke-tested on the Plate stress model:
  - two conversion warnings, dash-dotted links with the conversions in their tooltips;
  - the run gives thickness_m = 0.001, temperature_k = 293.15 and stress = 294.15.
