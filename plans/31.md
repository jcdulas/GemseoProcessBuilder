# 31 — Image export and report

Status: Done
Depends on: 21, 24, 25
SPEC: § 13

## Goal

Export any view as SVG or PNG, and generate a project report as standalone HTML and PDF.

## Scope

In:
- **Image export** (`File › Export › Image…` and a context-menu entry on each view): canvas (current level, or whole model expanded), N2, XDSM, every results chart.
  - SVG: serialize the view's SVG with computed styles inlined (only the properties used by our CSS), fonts as system fallbacks, `viewBox` fitted to content, white background.
  - PNG: render the standalone SVG in an offscreen `QWebEnginePage` (or `QSvgRenderer` if the SVG uses only supported features) at 1×, 2× or 4×.
  - Bridge method `image.export(svg, format, scale, path)`.
- **Report** (`File › Export › Report…`): options dialog to select the content of SPEC § 13 (project description, diagrams, component and variable inventory, problem definition, selected runs, selected post-processing images); output:
  - standalone HTML: one file, inline SVG, base64 images, print-friendly CSS, table of contents;
  - PDF: the same HTML printed with `QWebEnginePage.printToPdf` (A4, margins, page breaks before sections).
  - Report text in English, generated from the project data (no free-text AI generation).

Out:
- XDSM-specific exports (done in plan 25).

## Implementation notes

- `lib/svg_export.js` (pure, node tests):
  - The page reads the SVG elements and their computed styles into a tree of plain objects.
  - `serializeTree` writes it with a `style` attribute per element. Only the properties our CSS uses are written (fill, stroke…, fonts only on text), the SVG defaults are left out, and the page's `class`/`data-*`/event attributes are dropped. Fonts without a generic family get `Arial, Helvetica, sans-serif`.
  - `fitViewBox` fits the content with a margin; `standaloneSvg` adds the XML declaration, namespace, fitted viewBox, white background and title.
  - `pngSize` limits PNGs to 16 384 px per side.
- `services/export.js`:
  - `pictureOf(svg)`: an SVG drawn in the page becomes a standalone document.
  - `pngOf(picture, scale)`: the PNG is rendered by the page itself, drawing the SVG on a canvas. This is Qt WebEngine's Chromium, as the plan asked, but without an extra offscreen `QWebEnginePage`: the same renderer, fewer moving parts.
  - `exportImage`: format dialog (SVG, or PNG at 1×/2×/4×; for the canvas, the level shown or the whole model), then the save dialog, then `image.export`.
  - View sources are registered per center tab. File › Export › Image… exports the active tab, or the first chart shown in a results page. Every SVG of a results page (results tabs, surrogate quality charts) also has an "Export image…" context menu.
- Views:
  - canvas `picture({full})`: `buildScene`/`levelsToResolve` gained `expandAll`, so the whole model is drawn with every container expanded. It is drawn apart, out of sight in the body, without selection, zoom or run states. It must not be drawn in the canvas tab, which may be hidden: hidden elements have `display: none`. The background menu also has "Export image…".
  - N2 `n2Picture(view)`: the whole matrix with its row names. The view itself only draws the visible cells, so it cannot be exported as is.
  - XDSM `xdsmPicture`: exported at its natural size, with the zoom transform removed during the export.
  - N2 and XDSM toolbars have an "Export image…" button.
- App `app/image_export.py`: `image.export` checks the data (an SVG document, or a base64 PNG with its signature) and writes it with the extension of its format.
- Report:
  - `report/builder.py` (pure): `ReportOptions` (title; description, diagrams, inventory and problem switches; runs; post-processings) and `build_report` → one HTML file built from `report/templates/report.html` + `report.css` (`string.Template`, no Jinja). Sections:
    - description and project size;
    - diagrams inlined (XML declaration removed, as wide as the page at most, never wider than drawn);
    - inventory of the components (path, kind, source, port counts), with each component's variables (shape, unit, default, resolved global name, description);
    - problem definition per driver (formulation and algorithm with settings, design space, objectives, constraints as conditions, recorded outputs, parametric levels);
    - run summaries from `run.json`;
    - post-processing images embedded in base64.
  - Print CSS: A4 page, the contents on their own page, a page break before each section, no breaks inside tables and figures.
  - `report/pdf.py` `PdfPrinter`: `QWebEnginePage.printToPdf` on A4 with 14/16 mm margins. Pages live in the Qt thread and print asynchronously; `report.export` is a background method waiting for its job.
    - The first version waited in the Qt thread with a nested `QEventLoop`. It worked standalone (0.7 s) but hung when called from a bridge method, so it was rewritten.
  - `app/api_report.py`: `report.sources` (completed runs with their post-processing outputs that have images) and `report.export` (HTML, or PDF through a temporary HTML file).
  - `shell/report_dialog.js`: title (the project name by default), format, section checkboxes, runs and their post-processings. The diagrams are drawn out of sight: the whole model with containers expanded, the N2 of the model and of each driver (matrices of at least two entries), and the XDSM of each study (studies whose XDSM cannot be built are left out with a console warning).
- File menu: "Export image…" and "Export report…" after "Export Python script…".
- Tests:
  - `svg_export.test.js`: style map, serialization, viewBox, standalone document, PNG limits.
  - `test_builder.py` on the Sellar MDF example: every section, the selected sections only, inventory and problem contents, run summary, missing run, embedded images, and a standalone report (no `src`/`href` other than `data:` and anchors, no `<link>` or `<script>`).
  - `test_image_export.py`.
- Smoke-tested in the app on the Sellar MDF example:
  - Exports: canvas (level, and whole model at 881×330), N2, XDSM and the objective history chart, as SVG and as 2× PNG. The PNGs are sharp and the SVGs parse as XML; the PNGs are Chromium's own rendering of the exported SVG files.
  - Inkscape was not available here, so it was not tried.
  - The report of an optimization run was written as HTML (37 kB) and as a 6-page A4 PDF in 0.4 s.
  - Checking the PDF pages found two faults, now fixed: the empty workflow diagram (it was drawn in the hidden tab) and the XDSM exported at its zoom.
