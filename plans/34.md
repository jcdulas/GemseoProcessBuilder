# 34 — Modern interface

Status: Done
Depends on: 33
SPEC: § 8.1, § 8.2, § 14.1, § 14.6

## Goal

Give the application a modern, friendly look, close to n8n, instead of a classic desktop tool. The user asked for "a new, user-friendly interface that makes the user feel good about their work". Choices made with the user:

- light theme only;
- n8n-like cards with an icon;
- a canvas-first layout.

## Scope

In:
- **Visual identity**: new design tokens (neutrals, an indigo accent, vivid node type colors, radii, shadows, spacing), and the Inter font vendored (SIL OFL 1.1) so the interface looks the same on Windows and Linux.
- **Canvas-first layout**:
  - The native menu bar is hidden. A top bar holds the logo, the project name and its saved state, the undo/redo and view buttons, **Validate**, a prominent **Run** button, **Stop** while a run is going, and an application menu (every action of the former menu bar, with its shortcut, and the recent projects).
  - A thin icon rail on the left opens the drawers: Nodes (library), Tree, Problems (with a badge), Runs, Console, then Preferences and Help at the bottom.
  - Panels are floating cards (rounded, shadow) on a light background. The bottom panel is collapsed by default.
  - Center tabs are pills.
  - The status bar is slim and muted.
- **Canvas**:
  - dotted background that follows the zoom;
  - white rounded cards with a soft shadow, an icon tile colored by node type, the name, and a subtitle (kind, variable counts);
  - round ports;
  - an accent ring for the selection, a colored ring while running, a green check or a red mark after a run;
  - expanded containers as tinted frames;
  - floating zoom controls (zoom in, zoom out, fit);
  - a friendly empty state ("Add your first component").
- **Panels and controls**:
  - library rows with icon tiles and a one-line description;
  - inputs, selects, buttons, tabs, context menus, modals, the link panel and the search overlay restyled with the same tokens.
- **Feedback**: toasts, for example when a run completes (with a button to open its results) or fails, and when the project is saved.
- Pure, tested helpers:
  - the application menu built from the action definitions;
  - the node icon and label of each node kind.
- SPEC § 8.1 and § 8.2 updated; README screenshots retaken.

Out:
- A dark theme (the user chose light only).
- Changes to the behaviors of the canvas, the panels or the actions: this plan changes how the interface looks and where things are, not what they do.

## Implementation notes

- **Look**:
  - tokens in `css/tokens.css`: light neutrals, indigo accent `#5b5bd6`, vivid node colors, radii and shadows;
  - Inter 4.1 vendored as `static/vendor/fonts/InterVariable.woff2` (SIL OFL 1.1, recorded in `static/vendor/README.md` and `THIRD_PARTY_NOTICES.md`).
- **Frame**:
  - `shell/toolbar.js` builds the top bar and `ProjectTitle` (`app.projectTitle`); the saved state moved from the status bar to the top bar.
  - The application menu is built by `lib/app_menu.js` (pure, tested) from `actions.list`, and shown with the context menu component; recent projects come from `project.recent` and open with `project.open {path}`.
  - The native menu bar is built but hidden (`NativeMenus` calls `menuBar().setVisible(False)`). Native actions (Quit) run through the new `actions.triggerNative`, deferred with `QTimer.singleShot` so that the unsaved-changes dialog never opens inside a bridge call.
  - `shell/rail.js`: the icon rail. It shows a tab of the left or bottom panel, or hides the panel when that tab is already shown. `TabGroup.onBadge` feeds the Problems badge.
  - Panels are cards: the splitters are the 8 px gaps between them. The bottom panel starts collapsed (`PANEL_LIMITS.bottom.collapsed`), and saved layouts keep their state.
  - Validate opens the Problems only when there are errors or warnings; otherwise a toast says the model is valid.
- **Canvas**:
  - `lib/node_icons.js` (pure, tested) gives the icon, label and color family of each kind. The same icons are used on the canvas (SVG), in the library and in the tree (`nodeIconTile`).
  - Geometry: `NODE_WIDTH` 210, `HEADER_HEIGHT` 40, `PORT_ROW_HEIGHT` 20, `CARD_BODY_HEIGHT` 24 (cards are 64 px high). Saved positions are unchanged.
  - Each node has a ring (selection, running) and a shadow rect. Run states are a badge on the corner (`status.js`).
  - The dotted background is a CSS radial gradient on the container, moved with the zoom (`moveDots`). An SVG pattern halved the zoom frame rate.
- **Toasts** (`components/toast.js`): project saved, model valid, run completed (View results), failed (Details) or stopped. A failed run no longer opens a dialog by itself.
- **Fixes found on the way**:
  - The surrogate wizard drew its footer before its step had loaded, so Next stayed disabled until the user changed something. The navigation is now drawn again once the step is loaded.
  - `.button.bordered.primary` had no disabled look.
  - A global `[hidden] { display: none !important; }` rule, because the display of the classes hid the attribute (Stop was shown while disabled).
- **Performance** (SPEC § 14.1), on the reference model, with the machine lightly loaded (15-30 % of CPU from other programs):
  - The canvas is 39 % larger than before (643×685 px instead of 709×447 in a 1300×800 window), because the bottom panel starts collapsed. Zoom frame rates must be read with this in mind.
  - At first the zoom reached about 32 fps (41 before). At equal area, the old version would give about 30 fps, so the cards do not cost more per pixel.
  - To keep a margin, the shadows, subtitles and link counts are hidden while the view moves on levels of more than 120 nodes (`crowded` class).
  - Final values:

| Measure | Target | Plan 32 | Plan 34 |
|---|---|---|---|
| Project opening | < 3 s | 1.8 s | 2.1–2.7 s |
| Command p95 | < 100 ms | 37 ms | 39–45 ms |
| Validation, from the page | < 1 s | 0.34 s | 0.38 s |
| Canvas zoom, 300 nodes | ≥ 30 fps | 41 fps | 34–36 fps |
| Canvas pan, 300 nodes | ≥ 30 fps | 57 fps | 53–56 fps |
| N2 scrolling | ≥ 30 fps | 58 fps | 60 fps |
| Auto-layout, 300 nodes | < 2 s | 1.6 s | 1.6–1.8 s |

  - A full run with heavy load from other programs gave a command p95 of 142 ms and a Python validation of 1.6 s. Its Python validation is untouched by this plan, so that run was disturbed; measured again, the values are the ones above.
