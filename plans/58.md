# 58 — Segments and warm start

Status: Done
Depends on: 57
SPEC: [CLAUDE_PILOT_SPEC.md](../docs/CLAUDE_PILOT_SPEC.md) § 4.1, 4.2, 4.4, 4.5, 6.3, 8, 9.1

## Goal

`ClaudePilot`, usable in a plain GEMSEO script: it runs an optimization scenario in segments, calls Claude on its triggers without ever blocking the optimizer, applies the decisions that pass the guardrails between two segments, restarting from the best point with the evaluations already made, and records everything in a journal. Observer and Pilot modes; Advisor mode needs the application (plan 60) and falls back to Observer.

## Scope

In, in `plugins/gemseo_claude_pilot/`:
- `pilot.py`: `ClaudePilot(mode, allowed_actions, data_level, backend, …)` and `ClaudePilot.execute(scenario, algo_name, **settings)`, returning a `PilotResult`; the segment loop; the end of a segment at the next iteration boundary; the warm start from the best point; the final design point set to the best evaluation;
- `advisor.py`: the advisor, which builds the snapshots and the context, runs the detectors and the triggers, and exchanges with Claude, in a background thread (or inline, for tests and reproducible runs);
- `triggers.py`: periodic, event, start and end triggers, with a minimum interval between calls;
- `tools.py`: the answers to the read tools of § 6.3;
- `journal.py`: `journal.jsonl`, written as the run goes;
- `context.py`: a `pilot` section (mode, allowed actions, current segment);
- `snapshots.py`: histories built from a copy of the database entries, so that the advisor thread never reads the live database; a point whose constraints are missing is not feasible.

Out:
- The real backends, retries and budget (plan 59): without a backend, the pilot logs why and runs the scenario as is.
- Runner events and commands, Advisor mode, codegen (plan 60). Questions from the chat, the post-run report (plan 62). DOE, BiLevel and surrogates (plan 63).

  - triggers: period, minimum interval, events reported when they appear, not again while they last;
  - journal: records readable after the run, and after a run stopped by an exception;
  - tools: each read tool, in `no_code` and in `anonymized`; unknown names;
  - pilot, inline advisor: a decision to switch algorithm ends the segment, the next one restarts from the best point, no point is evaluated twice, the budget is respected; narrowed bounds are applied; stop ends the run; Observer mode applies nothing; a refused decision is not applied;
  - failures: three consecutive backend errors turn the pilot off, an authentication error at once; the run completes;
  - threaded advisor: a slow answer does not block the optimizer;

## Implementation notes

- **Open point 1**, settled on GEMSEO 6.3 and written in the spec's § 4.4: the end-of-segment exception of the new-iteration listener goes through `scenario.execute` and keeps the database, but not the current value, which the pilot sets to the best point; `max_iter` counts the iterations of one `execute`, points already in the database included (they are not evaluated again), so `max_iter` = evaluations left keeps the budget; each `execute` starts a new driver; GEMSEO does not check the current value against the bounds, so the pilot clips it.
- **`advisor.py`**, a module more than the spec listed (added to its § 3.1): the pilot's thread only copies the database entries (`database_entries`, arrays shared) and snapshots the problem every `check_every` evaluations (5); the history, the detectors, the triggers, the context and the call run in the advisor's thread. The point being started is left out of the copy: its outputs are not computed yet.
- **Snapshots**: a point whose constraints are missing has a NaN violation and is not feasible; the best point skips it.
- **Segments**:
  - the start and end calls wait for Claude (no optimizer runs then); the end call is only made when a segment ends by itself, and a decision there starts another segment;
  - at the end, the pilot gives back the bounds the user set and puts the design space at the best evaluation of the whole run; `scenario.optimization_result` stays the one of the last segment;
  - the budget is the user's `max_iter`, or the default of the algorithm's settings model;
  - a decision is applied at the next iteration boundary; one made more than 50 evaluations earlier is dropped (open point 5), and recorded as `expired`.
- **Modes**: Observer only allows `none`; the context tells Claude the allowed actions (a `pilot` section: mode, allowed actions, segment, budget), and a decision with an action is refused and sent back. Advisor falls back to Observer in a script, with a log message, until plan 60.
- **Without backend**, the pilot logs it and runs the scenario as is (`stop_reason` "no backend"); the real backends and their creation come with plan 59.
- **Threads**: the advisor's thread is a daemon; the end of a segment waits for the call in flight, bounded by the backend's timeout once plan 59 adds it.
- **Journal**: `journal.jsonl` in the folder named by `GEMSEO_CLAUDE_PILOT_FOLDER` (for the runner, plan 60), else `<script>.pilot/` next to the script; `journal=False` keeps it in memory (`pilot.journal.records`). A run stopped by an exception ends with a `status` record `interrupted`.
- **Tests**: `FakeBackend(script, then=...)` gives an answer once the script is over. The pilot tests run an analytic Rosenbrock scenario without MDA (about 25 ms), with the inline advisor so that they are reproducible, and one threaded test with a slow answer. A standalone Sellar script runs in two segments (SLSQP, then COBYLA from the best point) within its budget of 30 evaluations, with its journal.
