# 25 — XDSM view

Status: Done
Depends on: 16
SPEC: § 8.5, § 13 (XDSM export), § 17 (risk 5)

## Goal

Show the XDSM of a driver's process, produced by GEMSEO from the generated scenario and rendered in SVG with d3, with HTML and PDF exports.

## Scope

In:
- Worker method `xdsm.build(source)`: imports the generated script, calls `build_scenario()`, runs GEMSEO's XDSM generation to obtain the XDSM JSON (without opening a browser), returns it.
- Renderer decision: evaluate vendoring **xdsmjs** (license, d3 v7 compatibility, offline use, ability to theme with our tokens) against a custom d3 renderer of the XDSM JSON. Choose, record the decision in the notes and in SPEC § 17 risk 5.
- XDSM center tab: renders the XDSM of the selected driver (or the top driver), with zoom/pan, and the process animation steps if the chosen renderer supports them; refresh when the model changes (debounced, only when the tab is visible).
- Click on an XDSM discipline box selects the matching node (via the mapping sidecar).
- Exports: standalone HTML (renderer + JSON inlined) and PDF via pyxdsm when installed and LaTeX is available (menu item disabled with a tooltip otherwise).

Out:
- PNG/SVG image export shared by all views (plan 31).

## Implementation notes

- Worker (`workers/xdsm_methods.py`):
  - `xdsm.build(source)` imports the generated script, builds its scenario and returns `scenario.xdsmize(save_html=False)` as a dict: `root` plus one diagram per sub-scenario (`<Scenario>_scn-…`). A process target, or a scenario that cannot be built, gives a clear error.
  - `xdsm.capabilities` reports whether a PDF is possible: pyXDSM is installed here, but `pdflatex` is not on the PATH, so PDF export is disabled with that reason as tooltip.
  - `xdsm.pdf(source, path)` runs `xdsmize(save_pdf=True, pdf_build=True)`.
- Renderer decision (SPEC § 8.5 and § 17 risk 5): a custom d3 renderer of GEMSEO's XDSM JSON instead of vendoring xdsmjs.
  - `lib/xdsm_layout.js` (pure, tested): diagonal positions with the user in row and column 0, data blocks in the source row and target column (duplicated edges merged), data lines, and process steps from the nested workflow (loops return to their driver, `parallel` branches); readable labels (`x^(0)` → `x⁰`, `y^*` → `y*`, at most 5 names).
  - `views/xdsm/renderer.js` (`mountXdsm`): shapes by type, parallelogram data blocks, grey data lines, numbered process lines with arrows, a breadcrumb for sub-scenarios (double-click an `mdo` box), zoom, pan and fit. It needs only d3 and the layout.
  - `css/xdsm.css` uses the application tokens.
- App (`app/api_xdsm.py`): `xdsm.build` (generated script + worker, plus a name → node id map for the disciplines, the nested scenarios and the target), `xdsm.capabilities`, `xdsm.exportHtml`, `xdsm.exportPdf`.
- `app/xdsm_export.py`: standalone HTML with tokens, XDSM styles, d3, the layout and the renderer joined into one inline module (imports and `export` keywords removed) and the JSON (`</` escaped). A test checks the joined module with `node --check`.
- XDSM tab (`views/xdsm/xdsm_view.js`; View › XDSM; "Show XDSM" on drivers):
  - Follows the selection: the selected driver, else the study around the selection or level, else the first study.
  - Refreshes 0.8 s after a model change, only while visible (a stale tab rebuilds when shown).
  - A click on a box selects its node: the driver, a discipline, or a nested scenario. The MDAs created by formulations have no node.
  - Export HTML and Export PDF (disabled, with the reason) use the save dialog.
- Smoke-tested:
  - Sellar MDF (Optimizer, MDAGaussSeidel, 3 disciplines, 15 data blocks), Sellar IDF (parallel evaluations) and SSBJ BiLevel (10 boxes; double-click opens StructureOptimizer's own XDSM; clicks select the nodes).
  - The exported BiLevel HTML (300 KB) renders in a plain web view without network.
  - Content comes from GEMSEO's own XDSM JSON, so nodes, edges and workflow match GEMSEO's output.
