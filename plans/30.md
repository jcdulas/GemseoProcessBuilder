# 30 — Surrogates

Status: Done
Depends on: 16, 19
SPEC: § 7.4, § 12.1

## Goal

Build surrogate models from DOE runs of the project with a wizard, assess their quality, store them, and use them as components in any workflow.

## Scope

In:
- "Build surrogate" wizard, opened from a DOE run (Runs panel or Results tab) or from the Surrogate item of the library:
  1. choose the run (DOE or parametric), inputs and outputs (defaults: design variables and responses);
  2. choose the algorithm among GEMSEO regression models (RBF, GPR, polynomial, …) and its settings (generated form, plan 15);
  3. train in the worker (cancellable);
  4. quality: R², RMSE on training data and cross-validation (k-fold, k configurable), predicted-vs-observed chart per output, residual histogram;
  5. name and save.
- Storage: pickle in `<project>.surrogates/<name>.pkl` + metadata JSON (source run, variables, algorithm, settings, quality metrics, dates); project `surrogates` list updated.
- Component kind `surrogate`: ports from the metadata; inspector shows metadata and quality; "Retrain" (reopens the wizard pre-filled); "Show source run".
- If the source run is deleted, the surrogate stays usable; its metadata keeps the run id with a "source deleted" flag.
- Codegen: `SurrogateDiscipline` loaded from the pickle file (path relative to the script's project via a constant), with a comment explaining what the surrogate replaces.
- Example: Rosenbrock DOE → RBF surrogate → optimization on the surrogate (`examples/rosenbrock_surrogate.gpb.json`).

Out:
- Adaptive sampling / surrogate refinement loops (not in SPEC).

## Design

- Training tests use tiny datasets (≤ 30 samples, 2 inputs) to stay under one second; cross-validation test with k = 3.
- Pickles are loaded only in the worker or the runner, never in the UI process.

## Implementation notes

- New dependency: `scikit-learn` (BSD-3-Clause). GEMSEO's GPR, polynomial, linear and other regression models, and its quality measures, need it; without it only RBF, TPS and FCE are listed. It is recorded in `pyproject.toml` and in SPEC § 14.5–14.6, with SymPy, which was missing there. `THIRD_PARTY_NOTICES.md` comes with plan 33.
- Worker `workers/surrogate_methods.py`:
  - `surrogate.variables(folder)`: the design variables of the run as default inputs, the other variables as outputs, and the number of samples.
  - `surrogate.train(...)`:
    - builds an `IODataset` from `dataset.csv` through `results/reader.py`, leaving out the evaluations with NaN;
    - creates the model with `create_regression_model` (inputs and outputs scaled by `MinMaxScaler`, as `SurrogateDiscipline` does), then learns;
    - runs a k-fold cross-validation itself: a seeded shuffle, one model per fold trained with `learn(samples=...)`;
    - returns R² and RMSE per output component on the training data and by cross-validation, the points of the charts (at most 5 000) and the input ranges and centers;
    - pickles the model with `gemseo.to_pickle` into a training file.
  - A hand-written cross-validation keeps the cross-validated predictions for the charts, which GEMSEO's measures do not return.
  - Errors are explained: unknown model, missing variable, no input or output, invalid settings, fewer than 3 complete samples.
- Algorithms: a new kind `regression` in `algorithms.list` / `settings.schema` / `settings.validate` (`RegressorFactory`, without the composite `RegressorChain` and `MOERegressor`), so the settings form is generated as for drivers (plan 15). `essential_fields.js` gained `hiddenByKind` (hides `transformer`, `parameters`, `input_names`, `output_names`, `der_function`, `kernel`, `bounds`) and the essential regression settings.
- Storage `results/surrogates.py` (UI side, no pickle loading):
  - Metadata models: `SurrogateMetadata`, with source run, variables with ranges, algorithm, settings, quality, sample and fold counts, and dates.
  - `metadata_ports`.
  - `SurrogateStore`: `<project>.surrogates/<name>.pkl` + `<name>.json`, with the `Project.surrogates` index updated like the runs (no undo). It saves with unique names, and retraining replaces the files while keeping the id and creation date. It also handles deletion and missing files.
  - `source_deleted(run_id)` sets the "source deleted" flag, called through the new `RunStore.deleted_listeners`.
- App `app/api_surrogates.py`:
  - `surrogates.list`, `variables`, `train` (background, one at a time; `cancel` restarts the worker like post-processings), `save`, `use`, `add`, `delete`.
  - Only files from the training folder can be saved.
  - Saving (or `use`) sets the configuration of the components using the surrogate (`surrogate_id`, `model_path`, `summary`) and their merged ports in one undo step. Retraining updates every component using the surrogate.
- Surrogate component: `surrogate` joined the introspected kinds (Python and JS). The worker reads the ports from the metadata only: input defaults are the centers of the training data, and descriptions give the training ranges. A missing surrogate becomes an introspection error, and so a validation problem.
- Codegen:
  - `SurrogateDiscipline(from_pickle(ROSENBROCK_MODEL))` with a path constant, a one-time explanation of what a surrogate is, and a wrapped comment saying what this one is (model, sample count, run, variables).
  - `summary` is stored in the configuration, so the generated script reads no file.
  - Golden `rosenbrock_surrogate.py` uses a relative model path.
- UI:
  - `views/surrogate_wizard/`:
    - `wizard.js`: steps reachable in order, Back/Next, the Save step with "Add to model", and retrain pre-filling from the metadata;
    - `data_step.js`: completed runs, input/output checkboxes;
    - `algorithm_step.js`: common models first, generated settings form, number of folds;
    - `quality_step.js`: Train / Cancel, a quality table per output component, charts of the chosen row with cross-validated or trained predictions.
  - `views/results/predicted_vs_observed.js`: d3 predicted-vs-observed scatter with its diagonal and tooltips, and a residual histogram.
  - Entry points: a "Build…" button in the Runs panel (completed runs with ≥ 3 evaluations), "Build surrogate…" in the Results tab bar, and the inspector of surrogate components. The inspector shows the choice among the project's surrogates, the model, training data, update date and quality, plus "Retrain…" and "Show source run" (hidden when the run was deleted).
- Example `examples/rosenbrock_surrogate.gpb.json` (built by `tools/build_examples.py`): a DOE (LHS 30) of Rosenbrock and an SLSQP optimizer around an unbuilt Surrogate component. The project description gives the steps; no pickle is committed, since pickles depend on library versions.
- Tests:
  - worker: variables, RBF interpolation through `SurrogateDiscipline`, polynomial of degree 4 with R² = 1 by cross-validation, errors, listing and schemas;
  - storage: round trip, unique names, retraining, deleted run, missing files;
  - app controller with the worker functions in-process: train, save into a component and undo it in one step, retrain, add, delete, run deletion;
  - golden script;
  - equivalence with hand-written GEMSEO on a 20-sample RBF and SLSQP for 5 iterations.
  - `conftest.py` scans the regressors at collection time, because importing scikit-learn exceeds the 1 s limit.
- Smoke-tested in the app on a copy of the example:
  - The DOE ran (30 samples). The wizard was opened on its run for the Surrogate component; data, algorithm (RBF, generated form) and training were driven through the wizard's methods.
  - Quality: training R² = 1.000, cross-validation R² = 0.869 and RMSE = 231.9.
  - Saving set the component's configuration and ports; the inspector showed the metadata and quality.
  - The optimizer run completed on the surrogate: 15 evaluations, f = -34.5 at (0.62, 0.47). That minimum belongs to the RBF, not to the Rosenbrock function: 30 samples are few for Rosenbrock, as its cross-validation says.
