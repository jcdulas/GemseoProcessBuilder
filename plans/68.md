# 68 — Large-scale optimizer: GEMSEO plugin

Status: Done
Depends on: 67
SPEC: [LARGE_SCALE_OPTIMIZER_SPEC.md](../docs/LARGE_SCALE_OPTIMIZER_SPEC.md) § 3.9, 4, 6, 13 (open points 5, 7); SPEC § 6.4 (algorithms), 14.6

## Goal

`LSO_MMA` and `LSO_GCMMA` are GEMSEO algorithms: any `OptimizationProblem` runs on them, with the full Jacobians GEMSEO computes, or with the rows a discipline gives on request (row mode). They are listed in GEMSEO Process Builder and explained there.

## Scope

In:
- the entry point `gemseo_plugins`; `gemseo/library.py`: a `BaseOptimizationLibrary` with the two algorithms (handles inequality and equality constraints, requires gradients); `gemseo/settings.py`: the settings models deriving from `BaseOptimizerSettings`, `store_jacobian` forced to False;
- `gemseo/adapter.py`: the `LargeScaleProblem` of an `OptimizationProblem` — values through GEMSEO's functions (the database and its listeners see every evaluation), objective gradient, normalized bounds and rows (× the ranges), sign conventions, equality constraints;
- full-Jacobian mode: the rows of the working set taken from `constraint.jac(x)`, dense or sparse;
- row mode: the `RowJacobian` protocol (§ 6) on the discipline computing a constraint; the rows chained with the Jacobians of the disciplines between the design variables and that discipline when they are uncoupled; a clear error for a coupled chain (open point 5);
- prototype of open point 5: can GEMSEO's coupled adjoint (MDA) be seeded with selected output rows? Result in the notes, and in the spec;
- colored mode (plan 67): the sparsity pattern given by a step of the process — the setting `sparsity_pattern`, a function of the user's code called once at the start of the run with the design variables and the constraints as `(name, size)` in GEMSEO's order, returning a sparse boolean matrix (constraints × variables); a dense matrix is refused with a message (10 GB at 10⁵ × 10⁵); without `sparsity_pattern`, the matrix is taken as full and the optimizer runs without the sparse optimizations (the rows mode of plans 65 and 66); and the directional derivatives of the constraints through GEMSEO — prototype of open point 7 (the products of GEMSEO's `JacobianOperator`, or a `TangentJacobian` protocol on the discipline, like `RowJacobian`);
- in the application: the driver editor of an `LSO_*` algorithm gets a **"Colored Jacobians" checkbox, unchecked by default** (spec § 3.9, § 6); checked, it shows the "Sparsity pattern" field naming a Python function of a file of the project (like the Python function components) and the mode (`hybrid` by default, or `colored`); codegen passes `jacobian_mode` and `sparsity_pattern=build_pattern` only when it is checked, the script reader reads them back (checked when `jacobian_mode` is `colored` or `hybrid`);
- GEMSEO's stopping criteria and `max_time` honoured; the optimization result filled (status, message, number of rows);
- in the application: the algorithms listed when the plugin is installed in the Python of the runs; their explanation in the algorithm catalog (when to use them: many variables and constraints, few active, costly gradients); the Claude copilot's algorithm list gets them from GEMSEO like the others.

Out:
- the benchmarks (plan 69); piloting (plan 70).

## Implementation notes

- **Package**: `gemseo_lso.gemseo` (`library.py`, `settings.py`, `adapter.py`, `sources.py`), found by GEMSEO through the entry point `gemseo_plugins` (`gemseo-lso = "gemseo_lso.gemseo"`); the plugin now depends on `gemseo>=6.3,<7` and `pydantic` (already in the notices, with the application); the core still imports neither.
- **No Jacobian at the start**: GEMSEO evaluates every Jacobian at the starting point for the algorithms requiring gradients (10¹⁰ entries at 10⁵ × 10⁵). The library declares `require_gradient` (the application shows it) and shadows it with False on its instance while `_pre_run` runs; GEMSEO's KKT options (`kkt_tol_abs`, `kkt_tol_rel`, which need a stored Jacobian) are not offered: the optimizer has `kkt_tolerance`.
- **Settings**: every setting of the core except those GEMSEO owns (`max_iter`, which counts evaluations, `ftol_rel`, `xtol_rel`, `max_time`: the core's own criteria are off); `ineq_tolerance` and `eq_tolerance` default to 1e-5 (GEMSEO: 1e-4 and 1e-2), as the core; `store_jacobian` True is refused; the cross checks of the core run when the model is validated. The result: status 0 converged, 1 stalled…, and a message counting the constraint gradients and directional derivatives asked for.
- **Row mode, automatic per constraint** (the spec had the full Jacobian by default and the row mode on request): an inequality constraint whose discipline offers `compute_jacobian_rows` is given row by row; the others keep GEMSEO's full Jacobian, computed once per point. The disciplines are found through the adapters of the problem's functions — a private attribute of GEMSEO 6.3 (`_DisciplineAdapter__discipline`), pinned by a test; without it the full Jacobian is used — then among the leaves of the chains and MDAs, by output name. The sign of a constraint `g >= value` is read in its representation (only the sign matters for the rows).
- **Differentiated outputs detached**: GEMSEO linearizes a discipline for all its differentiated outputs at once, so the gradient of the objective computed the whole Jacobian of the constraints of the same discipline (16 full Jacobians in the first test run). During the run, the outputs given row by row (and in the `colored` mode, those of every constraint whose discipline is known) are removed from `_differentiated_output_names` of their disciplines and of the chains containing them, then put back — unless the objective or an equality constraint needs them.
- **Upstream disciplines**: the inputs of a row-giving discipline that are not design variables are computed by an `MDOChain` of their producers (in dependency order) and differentiated by it; a cycle, or a discipline in an MDA of several disciplines, is refused with a message naming open point 5.
- **Open point 5, prototype**: `JacobianAssembly.coupled_system.adjoint_mode` takes the rows of ∂g/∂x and ∂g/∂y as its seeds and returns exactly those rows of the coupled total derivatives (Sellar with vector couplings of size 6, rows 1 and 4: identical to GEMSEO's full adjoint), one adjoint solve per row; the Jacobians of the coupled disciplines are still computed in full. Not wired: a coupled row-giving discipline is refused (spec § 13).
- **Open point 7**: the `TangentJacobian` protocol on the discipline (spec § 6), chained like the rows; used when every inequality constraint has one, finite differences on GEMSEO's values otherwise. `JacobianOperator` was not used: it is built within `linearize`, for all the outputs.
- **Pattern function**: called once, with the design variables and the inequality constraints as `(name, size)`, the name of a constraint being its output when it has one; checked by the core (sparse, shape, no empty row).
- **Application**: `DriverConfig.colored_jacobians` (`enabled`, `mode` `hybrid` or `colored`, `module_path` or `module`, `function`), stored apart from the algorithm settings so that GEMSEO's validation of the settings is untouched; project paths converted in the objects of a driver configuration too; the rule `colored_jacobians` (checked without a function: an error); the editor block under the algorithm card of `LSO_*` algorithms (`panels/driver_editor/colored_jacobians.js`), unchecked by default; `jacobian_mode` and `sparsity_pattern` hidden from the generated form (the latter is left out of the schema anyway); codegen imports the function in `execute_scenario` (or the nested scenario's function) like a Python function component, with a comment; the script reader takes `jacobian_mode` and `sparsity_pattern` out of the settings back into `colored_jacobians`, with a warning for a non-LSO algorithm; golden script `sellar_mdf_colored`. The guide gives both algorithms a family of their own, "Gradient-based, large-scale"; the suggestion of an algorithm is unchanged (it does not know whether the plugin is installed). The Claude copilot may not change `jacobian_mode` nor `sparsity_pattern` (`MANAGED_SETTINGS`) until plan 70.
- **Tests**: Sellar (MDF) against SLSQP with both algorithms; the constrained Rosenbrock with LSO_GCMMA against SLSQP's and NLOPT_MMA's optimum written as a constant (SLSQP alone takes more than a second there; LSO_MMA cycles, then switches to GCMMA: over a second, not tested); the plugin's `conftest.py` runs a small MDF scenario once (GEMSEO loads its factories lazily: 0.7 s the first time).
- **Acceptance**: a GEMSEO scenario of 10⁵ variables and constraints in row mode (LSO_GCMMA, DisciplinaryOpt) converges in 20 iterations and 8 s, 1.2e-3 from the known solution, asking for about 10,000 rows per iteration and never for a whole Jacobian.

- **Later, in plan 69**: the `colored` mode removed (plan 67); the driver editor lost its mode select: checked, the colored Jacobians are the `hybrid` mode, and the project keeps no mode.
