# 14 — Code generation core

Status: Done
Depends on: 13
SPEC: § 10 (all), § 5.2, § 6.1, § 1.2 (principles 1 and 5)

## Goal

Build the code generator that turns a project into a readable, standalone GEMSEO script, covering disciplines, remappings, namespaces, assemblies and the MDA driver. Scenario drivers are added in plan 16 on top of this core.

## Scope

In:
- Generator architecture producing Python source with sections, comments and helpers per SPEC § 10.2.
- Naming: snake_case Python identifiers derived from node names, unique within the script, never ids; reserved words and GEMSEO API names avoided.
- Disciplines: analytic (explicit class import and `AnalyticDiscipline({...}, name=...)`, which reads better than the string-based factory), python function (`AutoPyDiscipline`), python class (import + constructor with `init_args`).
- Remapping (`RemappingDiscipline`) when global names differ from local names; namespaces for isolated nodes.
- Assemblies: `MDOChain`, `MDOParallelChain`, `MDAChain` (with settings), `transparent` flattening.
- MDA driver and model without driver: build the MDA and execute it once with the input values.
- Sidecar mapping file `script.gpb-map.json` (discipline name → node id).
- Output already formatted by the writer; `ruff format --check`, `ruff check` and `mypy` enforced in tests.
- `codegen.export(driverId, path)` bridge method and `File › Export › Python script…` action.
- Golden-file tests.

Out:
- MDO/DOE scenarios, formulations, design spaces (plan 16); unit conversions and N-D flattening (plan 27); executable wrapper and surrogate disciplines (plans 28, 30); nested drivers (plan 23).

## Design

- The writer is a thin structured string builder, not an AST library: the output must look hand-written (blank lines, grouped imports, short comments).
- The generator walks the project once, collects needed imports, then emits in this order: module docstring, imports, constants (if any), `build_disciplines()` (or one builder per assembly when that keeps functions under ~40 lines), `build_mda()` / `build_scenario()`, `main()`, `if __name__ == "__main__":`.
- User-typed numbers keep their text form: the project stores the original string alongside the value for design-space and default values (add this to the model now if missing, with a migration).
- Comment templates are written once per concept (MDA, remapping, namespace, chain vs parallel) in plain English, per § 10.2.
- `ruff` is **not** a runtime dependency: the writer itself emits formatted code (line length 88, black-compatible wrapping of long calls with one argument per line). Tests enforce it with `ruff format --check` on the golden files. Update SPEC § 10.2 "Formatting" accordingly ("formatted as `ruff format` would", checked in tests).
- Golden tests compare the generated source with the stored file; a helper `--update-golden` flag rewrites them; any change must be reviewed by a human (note in the test docstring).

## Implementation notes

- `codegen/` modules:
  - `pretty.py` lays out calls, lists and dicts with black's rules, so the output needs no formatter;
  - `naming.py`, `literals.py` (typed text such as `1e-6` is kept), `writer.py` (import sections in ruff's default isort style, with grouped names);
  - `context.py`, `disciplines.py` (analytic, python function, python class, `RemappingDiscipline`), `structure.py` (chains, parallel chains, MDAs, transparent flattening, one `build_<assembly>()` per assembly);
  - `generator.py` (`generate()`, `write_script()` writing the `*.gpb-map.json` sidecar).
- Contract for targets without scenario: `build_disciplines()`, `build_process()` and `main()`. `main()` passes the input values typed in the diagram (`default_text` set, not computed by any discipline) as NumPy arrays. SPEC § 10 is updated.
- Isolation goes through `RemappingDiscipline` (`Front:mass`), not the namespaces API, so scripts have a single renaming mechanism. SPEC § 5.2 is updated.
- A chain runs its children in dependency order, using `core.graph.execution_order`, a stable topological sort over the strongly connected components. Without it, a chain drawn "Cost, Area" computed the cost from the default area.
- Scenario drivers raise `CodegenError` until plan 16. Nested drivers raise it until plan 23.
- `codegen.export {target?, path?}` asks for the path next to the project when `path` is missing. `codegen.preview` returns the source. The `File › Export Python script…` action exports the selected container, or else the level shown.
- Golden projects are built in Python (`tests/python/golden_projects.py`) instead of stored `.gpb.json` files. They are easier to read and review. Scripts are in `tests/python/codegen/golden/`, rewritten with `pytest tests/python/codegen --update-golden`.
- Quality: ruff check with ruff's defaults plus E, F, W, I, N, UP, B, SIM, RUF and D, and ruff format --check, run in pytest (70 ms each). The golden folder is excluded from the repository's ruff config. `mypy --strict` on the golden scripts takes 2.6 s cold, so it runs as the separate `mypy scripts` step of `tools/check.py`.
- Execution tests import each golden script. The Sellar MDA matches hand-written `create_mda` to 1e-8. The other scripts print the expected values. The first `create_mda` scans GEMSEO's MDA factory (0.2 s), so `conftest.py` warms it up.
- Smoke-tested in the app: Sellar was exported through the bridge and the exported script ran standalone (`obj = 0.80529889`, `y_1 = 0.8`, `y_2 = 1.8`). Exporting a component target shows "Only the model, an assembly or a driver can be run."
- Self-review against § 10.2: one short function per step, in reading order; one comment per concept (MDA loop with its variables, remapping, chain vs parallel); no ids in the code; typed signatures; readable imports.
