# 14 — Code generation core

Status: Not started
Depends on: 13
SPEC: § 10 (all), § 5.2, § 6.1, § 1.2 (principles 1 and 5)

## Goal

Build the code generator that turns a project into a readable, standalone GEMSEO script, covering disciplines, remappings, namespaces, assemblies and the MDA driver. Scenario drivers are added in plan 16 on top of this core.

## Scope

In:
- Generator architecture producing Python source with sections, comments and helpers per SPEC § 10.2.
- Naming: snake_case Python identifiers derived from node names, unique within the script, never ids; reserved words and GEMSEO API names avoided.
- Disciplines: analytic (explicit class import and `AnalyticDiscipline({...}, name=...)`, which reads better than the string-based factory), python function (`AutoPyDiscipline`), python class (import + constructor with `init_args`).
- Remapping (`RemappingDiscipline`) when global names differ from local names; namespaces for isolated nodes.
- Assemblies: `MDOChain`, `MDOParallelChain`, `MDAChain` (with settings), `transparent` flattening.
- MDA driver and model without driver: build the MDA and execute it once with the input values.
- Sidecar mapping file `script.gpb-map.json` (discipline name → node id).
- Output already formatted by the writer; `ruff format --check`, `ruff check` and `mypy` enforced in tests.
- `codegen.export(driverId, path)` bridge method and `File › Export › Python script…` action.
- Golden-file tests.

Out:
- MDO/DOE scenarios, formulations, design spaces (plan 16); unit conversions and N-D flattening (plan 27); executable wrapper and surrogate disciplines (plans 28, 30); nested drivers (plan 23).

## Design

- The writer is a thin structured string builder, not an AST library: the output must look hand-written (blank lines, grouped imports, short comments).
- The generator walks the project once, collects needed imports, then emits in this order: module docstring, imports, constants (if any), `build_disciplines()` (or one builder per assembly when that keeps functions under ~40 lines), `build_mda()` / `build_scenario()`, `main()`, `if __name__ == "__main__":`.
- User-typed numbers keep their text form: the project stores the original string alongside the value for design-space and default values (add this to the model now if missing, with a migration).
- Comment templates are written once per concept (MDA, remapping, namespace, chain vs parallel) in plain English, per § 10.2.
- `ruff` is **not** a runtime dependency: the writer itself emits formatted code (line length 88, black-compatible wrapping of long calls with one argument per line). Tests enforce it with `ruff format --check` on the golden files. Update SPEC § 10.2 "Formatting" accordingly ("formatted as `ruff format` would", checked in tests).
- Golden tests compare the generated source with the stored file; a helper `--update-golden` flag rewrites them; any change must be reviewed by a human (note in the test docstring).

## Tests

- Naming: collisions, reserved words, non-ASCII names.
- Literals: `1e-6` preserved, arrays, nested dicts.
- Golden comparisons, lint/type checks, numerical equivalence on Sellar MDA.

## Acceptance criteria

- The exported Sellar MDA script runs standalone with `python script.py` and a two-year-experience developer can follow it (self-review against § 10.2 checklist, recorded in the notes).
- `python tools/check.py` passes.
