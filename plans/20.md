# 20 — Results views I: summary, history, table

Status: Done
Depends on: 18, 19
SPEC: § 12.2 (Summary, History, Data table), § 11.5 (live history)

## Goal

Open a Results tab per run with the Summary, History and Data table views, working both for finished runs and live during a run (replacing the live chart of plan 18).

## Scope

In:
- Results tab framework: one center tab per opened run, with sub-tabs; opened from the Runs panel, automatically when a run starts, and restored for the last opened run.
- **Summary**: status, duration, evaluations, optimum (design variables, objectives, constraints with active/violated indicator and margin), best feasible point, algorithm and formulation used, link to the script.
- **History**: objective, constraints (with threshold line), normalized design variables vs. iteration; log/linear toggle; hover readout; live updates during a run.
- **Data table**: virtualized table backed by `results.rows` paging, sort, filter builder, column chooser, CSV export of the current view.
- Chart component basics reused by plan 21: axes, scales, tooltip, legend, resize handling.

Out:
- Scatter matrix, XY, parallel coordinates, parametric views, comparison (plan 21).

## Design

- Load the `dataviz` skill before writing chart code; colors come from CSS tokens.
- Live mode: the History view reads from the run state service of plan 18; after `run.finished` it switches to worker-backed data transparently.
- The Data table requests pages ahead of the scroll position (one page of prefetch each way).

## Implementation notes

- Pure libraries, tested in `tests/js/results_libs.test.js`:
  - `lib/chart_scales.js`: `extent` as a loop (spreading 100k values overflows the stack), linear domains with a margin for constant data, log domains refused when values are not all positive, one tick every ~80 px;
  - `lib/normalize.js`: scaling between bounds, `null` for degenerate or infinite bounds, per-column bounds from a design space;
  - `lib/paged_rows.js`: a page cache with one page of prefetch each way, invalidated when the query changes, and late answers of an old query ignored;
  - `lib/constraints.js`: a constraint at the optimum is active, violated or satisfied (with its margin) under GEMSEO's default tolerances.
- Chart basics (`charts/`):
  - `axis.js`: axes with light grid lines, labels, series colors taken from the CSS tokens, compact number format;
  - `tooltip.js`: a floating readout kept inside the window; `legend.js`: HTML swatches, dashed lines for equality constraints;
  - `line_chart.js`: series against the evaluation number, optional log scale (falls back to linear with a note when a value is not positive), threshold lines, and a hover rule with the value of each series. Curves are decimated to 2,000 points, and redraws are batched per frame and on resize.
  - No `dataviz` skill is available here; the charts follow its principles.
- Results tab (`views/results/`):
  - `results_tab.js`: one center tab per run with Summary, History and Table, opened from the Runs panel, and on History when a run starts (it replaces the plan 18 live chart, now deleted). The last opened run is reopened with the project (`view.extra.last_results`, not undoable).
  - `source.js`: live data from the run state (the accumulator now keeps every value of each iteration or sample, flattened like the table's columns, with roles from the driver configuration), then `results.summary`, `results.columns` and `results.history` once the run has finished; the switch happens on `run.finished`.
  - `summary.js`: driver, status, duration, evaluations, algorithm, formulation and versions; the optimum (objective, design variables); constraints at the optimum (active, violated, or satisfied with margin); the best feasible point from `results.rows` (sort by objective, filter `feasible == 1`); buttons to open the script or the log, show the folder, and export to CSV.
  - `history.js`: objective (or outputs for a DOE) with a log toggle; constraints with a threshold at 0 (equalities dashed); design variables scaled between their bounds (raw values when some bound is missing).
  - `data_table.js`: a virtualized table of 22 px rows backed by `results.rows` (pages of 200); sort by clicking a heading (ascending, descending, off); a filter builder (column, operator, value, removable chips); a column chooser; export of the current view (visible columns, sort, filters) to CSV. It shows a message during a live run.
- Backend additions:
  - the runner records the constraint values at the optimum and the bounds of the design variables;
  - the sidecar carries the algorithm and the formulation, copied into `run.json`;
  - `runs.openFile` opens `script.py`, `run.log` or the project snapshot with the system application.
- Smoke-tested on Sellar MDF:
  - Summary gives SLSQP/MDF, `obj = 3.183` (GEMSEO's optimum), `c_1` active and `c_2` satisfied (margin 20.24), and the best feasible point is evaluation 8;
  - History shows 3 charts, updated live during a new run;
  - the Table sorts by `obj` (8, 7, … 1) and the filter `obj < 4` keeps 6 rows.
