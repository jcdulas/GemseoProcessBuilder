## Goal

The outer loop of a structural sizing is a pattern, not a component: engineers get a working study to start from. A DOE over the viable variants of the frame and stringer counts chains the topology planner of `nastran_architecture` (which makes a requested architecture viable and gives its topology plan), an external producer that builds from the plan (the stand-in of `nastran_refmodels`, wrapped as an executable component), the simplified loads of `nastran_loads` and the inner sizing of `gemseo_nastran`, with file caches and two local processes. Milestone M4 of the sizing loop (ECOSYSTEM-EVOLUTIONS.md § 6).

The chain follows the owner's decisions of 2026-10-11: architecture parameters → `nastran_architecture` (the request adjusted to the nearest viable configuration, a viability report) → the producer (the CAD, building from the plan) → `nastran_layout` (the delivery checked against the plan) → `nastran_loads` → the sizing. [SIZING_LOOP_EVOLUTIONS.md](../docs/SIZING_LOOP_EVOLUTIONS.md) § 6 is the record of GPB-E5 before the planner; this plan supersedes its chain and its full factorial.

## Implementation notes

- Built against `gemseo_nastran` 7672a4e (its outer loop, its own `examples/architecture_study`), `nastran_architecture` 44d90e9, `nastran_refmodels` 852ad7a. The folder is `examples/architecture_study/` (not `architectureStudy/`): an example written from a fixture project lives in a folder named after its script, as `external_code/` (the test of the examples requires it).
- Deviations from the plan, following what the packages built:
  - The producer is `gemseo_nastran`'s `ModelProducer` (the delivery accepted by `nastran_layout` against the plan, kept in the store, its initial mass for the loads), calling the stand-in `nastran_refmodels:produce` with the plan; no `producer.gpbwrap.json`. `nastran_refmodels` has no command line, and an executable component would lose the acceptance and the outputs `LoadModel` reads. A real CAD is given to `ModelProducer` as a command (its tokens `{parameters_file}`, `{folder}`, `{plan_folder}`); the README says so.
  - A parametric study over the stringer counts of the crown and of the upper sides (4 and 5), not a `CustomDOE` on `viable_variants.csv`: the viable variants of the box of `gemseo_nastran`'s example form this full grid, and GPB's DOE driver has no samples file (a later plan could add one). A non-viable request would be adjusted by the planner, and two requests snapping to one architecture are evaluated once by the store.
  - No HDF5 cache: two processes, which GEMSEO refuses with an HDF5 cache on Windows (the rule of plan 77 would make the project invalid there); the store of `gemseo_nastran` is the cache of the study across runs, processes and crashes.
- Open point 12 decided: no constraints on DOE and parametric drivers; the feasibility is a response (`feasible`), the views color by it.
- Codegen fix found on the way: a parametric study ignored `n_processes`; it is now passed to `CustomDOE`. And a file cache now creates its folder (`CACHE_FOLDER.mkdir(...)`, once per folder): GEMSEO creates the HDF5 file, not its folder, so the default `caches/` failed on a first run.
- The fixture project was written by introspecting the four classes with GPB's worker code in the environment of `gemseo_nastran` (its venv, with the sources of `nastran_architecture`, `nastran_refmodels`, `nastran_loads`, `nastran_layout`, `nastran_lcs`, `nastran_smear` on its path); the outputs that are paths were given the type `str`. The request and the description of `gemseo_nastran`'s example are inline in the constructor arguments (plain values); `store_path` keeps its default.
- The script is checked by `test_example_scripts.py` (its golden file is the example itself), `mypy` with `gemseo_nastran` ignored when missing (`pyproject.toml`). The pattern test with fakes (`codegen/test_architecture_pattern.py`, 0.2 s): a planner snapping a count to an even one, a producer and a sizing cached in an HDF5 file; two requests snapping to one architecture are produced and sized once, a run again on the file computes nothing.
- Demos: a docstring sentence "It needs the packages a, b and c in the Python of the runs." gives `Demo.requires`; `demos.list` (now in the background) asks the worker which are missing (`catalog.missing`, locating without importing) and the Library notes them.
- Run by hand, standalone (`python architecture_study.py`, two processes): 3 min 53 s for the four architectures, 22 s run again on its store with the same dataset; masses 320–326 kg, none feasible with the short sizing of the example. `tools/smoke_installed.py` runs it when the four packages are installed and skips it otherwise. Not done: the run from the window of the application, killed and resumed (the store makes the resume of plan 78 cheap: an architecture sized is read back from it).
