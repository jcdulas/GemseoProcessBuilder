# 12 — Link editing on the canvas

Status: Done
Depends on: 11
SPEC: § 5.1, § 5.3, § 5.4, § 8.2 (links, editing), § 8.7 (link inspector)

## Goal

Show the resolved variable flow on the canvas and let users create, inspect and delete links, following the hybrid linking model.

## Scope

In:
- Rendering from the resolver output at the current level:
  - explicit links: solid;
  - implicit couplings: dashed;
  - feedback edges: dedicated color and backward routing;
  - aggregated links between containers: single curve with a count badge;
  - free inputs of the level: small stub on the port.
- Link drawing gesture: drag from an output port to an input port (or the reverse), with live compatibility feedback (dtype and shape; unit feedback is added in plan 27): target ports highlighted green/red, tooltip with the reason.
- Commands: `addLink` / `deleteLinks` (plan 05) now also trigger resolver updates; `setGlobalName` (override) and `setIsolated`.
- Link hover tooltip (variables, producer, consumers), port hover highlighting its producer and consumers.
- Link inspector: variables, producer, consumers, explicit/implicit, "Convert to explicit link", "Delete link".
- Inspector Variables table: new **Global name** column (editable override, reset button) and a coupling indicator.
- Expose a port by dragging it onto the parent container background (sets it as an exposed port of the container; for drivers the full semantics come in plan 23; for assemblies it pins the derived port visible when collapsed).
- Context menu: "Isolate namespace" toggle on components and assemblies.

Out:
- Validation messages and quick fixes (plan 13), unit checks (plan 27).

## Design

- The canvas asks the resolver for the current level after each patch (`resolution.updated` event carries the touched scopes) and re-joins link elements keyed by `(from node, from port, to node, to port)`.
- Dropping a link on an input that already has an explicit producer asks for confirmation ("Replace the existing link?") and replaces it in one transaction.
- Implicit couplings cannot be deleted directly; the tooltip explains how (rename the variable or isolate the component) and offers "Isolate namespace".

## Implementation notes

- **Couplings drawn from the resolver**: the canvas asks `resolve.levels {levels}` (new batch method) for the current level and every container expanded in place, after each document change and level change; `lib/scene.js` now builds links from these level views instead of the stored links. Kinds: explicit (solid), implicit / coupled by name (dashed), feedback (orange, routed under the nodes by `lib/link_routing.js`), aggregated (one thick link with a count when more than 4 variables couple the same pair).
- **Containers show derived ports** (global names), so couplings to and from assemblies and drivers attach to named ports; expanded containers show their children instead. Free inputs (no producer in the scope) have an orange port.
- **Link drawing**: drag from any component port to a port of the opposite direction on another component (either way round); compatible targets turn green, refused ones red with the reason in a hint bar (`lib/link_compat.js`: text vs numbers, float into int, complex, different known sizes; unknown sizes give a warning). Dropping on an input that already receives a link asks before replacing it (one undo step: `deleteLinks` + `addLink`). Ports of containers cannot be linked directly: links always join component ports.
- Hovering a port highlights its links; hovering a link shows its variables in a tooltip; clicking a link shows a "Coupling" section in the inspector with, per variable, "Delete link" (explicit) or "Make explicit" (coupled by name) when both ends are components.
- **Global names**: new undoable command `setGlobalName {id, port, direction, global_name | null}`; the Variables table has an editable "Global name" column (overrides show "(set)") and a "Coupled with" column, both from `resolve.node`.
- "Isolate variable names" toggle in the node context menu (components and assemblies).
- "Expose a port by dragging it onto the container background" was not implemented: containers already show all their derived ports; exposing variables of nested drivers is done in their Interface tab (plan 23).
