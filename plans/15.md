# 15 — Driver configuration and generated forms

Status: Done
Depends on: 14
SPEC: § 6.2, § 6.4, § 8.6, § 9.1 (driver rules)

## Goal

Let users configure MDA, DOE, Optimization and Parametric study drivers through a driver editor whose algorithm, formulation and MDA settings forms are generated from GEMSEO's Pydantic settings schemas.

## Scope

In:
- Driver config models (extend `core/model.py`): design space entries, objectives, constraints, observables/responses, algorithm (name + settings), formulation (name + settings), execution options, parametric levels. Values keep their typed text (see plan 14).
- Worker methods:
  - `algorithms.list(kind)` for `optimization | doe | mda | formulation | surrogate | post_processing`, with capabilities (handles equality/inequality constraints, requires gradient, multi-objective, integer variables);
  - `settings.schema(kind, name)` returning `model_json_schema()` and default values.
- JSON Schema form generator (`forms/`): types, enums, arrays, bounds, defaults, descriptions as tooltips, nested objects; "Advanced" section for non-essential fields, driven by a maintained list of essential fields per common algorithm (`forms/essential_fields.json`).
- Driver editor in the inspector and full-panel mode (double-click on the driver header), tabs of § 6.4 except "Interface" (plan 23).
- Variable pickers: design variables only among the free inputs of the driver scope; objectives, constraints and responses among the outputs. Vector editing element-wise or with one broadcast value.
- Algorithm list with incompatible algorithms grayed out and the reason as a tooltip.
- DOE "Responses" abstraction (first response = objective, others = observables), hidden in simple mode.
- Parametric study tab: variables with levels (`linspace(lower, upper, n)` or explicit list).
- Canvas/tree context menu shortcuts: "Set as design variable / objective / constraint / response" opening the editor pre-filled.
- Driver rules added to validation: variable not a free input, missing objective or response, inconsistent bounds, initial value out of bounds, incompatible algorithm, multi-objective not supported.
- Roles column in the Variables table and role icons in the tree.
- Command `setDriverConfig` (undoable, with field-level granularity to keep undo labels meaningful).

Out:
- Code generation for scenarios (plan 16), nested driver Interface tab (plan 23).

## Implementation notes

- Driver configuration:
  - `core/drivers.py` defines Pydantic models (`DriverConfig`, `DesignVariable`, `Objective`, `Constraint`, `Choice`, `Level`, `Execution`).
  - The configuration stays plain JSON in `DriverNode.config`, so the file format is unchanged and no migration is needed. Defaults are left out when stored.
  - Typed text is kept: `DesignVariable.texts` holds a single value typed to fill a vector, and `Constraint.value_text` the constraint value as typed.
  - An empty algorithm or formulation name means the kind's default: SLSQP/MDF, LHS/DisciplinaryOpt, CustomDOE for parametric studies, MDAChain for MDAs. Saving settings stores the effective name.
- `SetDriverConfig {id, field, value}` changes one field and validates the whole configuration. Its undo label depends on the field ("Change design variables"…).
- Worker (`workers/algorithms_methods.py`):
  - `algorithms.list(kind)` covers optimization, doe, mda and formulation. Capabilities come from `ALGORITHM_INFOS`.
  - `settings.schema(kind, name)` uses a lenient schema generator that leaves out fields JSON cannot hold (arrays, callables, coupling structures).
  - `settings.validate` returns Pydantic errors as `{field, message}`.
  - Surrogates and post-processings will be added by the plans that use them.
- The bridge now sends `Infinity` and `NaN` as `null`: GEMSEO defaults such as `kkt_tol_abs = inf` would otherwise break `JSON.parse` in the page.
- App:
  - `AlgorithmService` caches lists and schemas until the worker restarts, and preloads the optimization capabilities once GEMSEO is ready, so validation can use them.
  - `DriverService` provides `driver.variables` (free inputs and outputs of the scope, for the pickers), `driver.algorithms` (each algorithm with why it cannot be used), `driver.portRoles` and `driver.assignRole`.
- Rules (`core/rules/drivers.py`):
  - errors: `invalid_driver_config`, `design_variable_not_free`, `text_design_variable`, `inconsistent_bounds`, `value_out_of_bounds`, `empty_levels`, `missing_objective`, `missing_response`, `not_an_output`, `text_output`, `unknown_algorithm`, `incompatible_algorithm` (constraints, several objectives, integers);
  - `unused_output` now ignores outputs a driver uses;
  - `incompatibilities()` is shared by the rule and by the grayed-out algorithm list, so there is a single source of truth.
- Page:
  - `lib/schema_to_form.js` (pure) handles `$ref`, `anyOf`/null, enums, bounds, arrays, nested objects and JSON fallbacks. Descriptions are cleaned of Sphinx markup.
  - `forms/schema_form.js` shows essential fields first and advanced fields in a `<details>`, with placeholders showing the defaults, changed settings in bold, and errors under each field.
  - The essential fields table is `forms/essential_fields.js` rather than a JSON file, because `fetch` does not support the `gpb://` scheme.
- Driver editor (`panels/driver_editor/`):
  - Tabs are grouped into three modules by similarity: `inputs_tabs.js` (design variables, levels), `outputs_tabs.js` (objectives, constraints, observables, responses) and `settings_tabs.js` (algorithm, formulation, MDA settings, execution).
  - The editor appears in the inspector, and full-panel in a dialog (⤢ button, double-click on a driver header, "Edit driver…" in the menu). Tables refresh in place, and forms keep the focused field.
- Roles:
  - Right-clicking a port on the canvas or in the tree offers "Set as design variable / objective / constraint", "Add as observable / response" or "Vary in the parametric study". The entry is filled from the port (size, default value, integer type) and the full editor opens on the right tab.
  - The Variables table has a Role column, and the tree shows role badges (DV, OBJ, CON, OBS, RES).
- The DOE "first response = objective" rule is explained in the Responses tab. The simple/expert display mode is not part of the UI yet.
- Tests:
  - Python: `test_drivers.py`, `test_rules_drivers.py` (one case per rule), `test_algorithms_methods.py` (real GEMSEO), `test_api_drivers.py`, and the `Infinity` case in `test_bridge.py`. GEMSEO factories are warmed up in `conftest.py`.
  - JS: `schema_to_form.test.js` runs on schemas captured from GEMSEO (SLSQP, COBYQA, LHS, MDAGaussSeidel, MDF). NLOPT is not installed, so COBYQA replaces NLOPT_COBYLA. Plus `driver_config.test.js`.
- Smoke-tested on a Sellar optimization:
  - pickers list the free inputs (`x_shared:2`…) and the outputs;
  - roles are assigned from the menu, and the editor opens on the right tab;
  - with a constraint, NELDER-MEAD, L-BFGS-B, TNC and DUAL_ANNEALING are grayed out with "does not handle inequality constraints";
  - the SLSQP form shows max_iter and the tolerances first; `max_iter = -3` is rejected by Pydantic with "Input should be greater than 0".
- Codegen: `chain` assemblies keep the displayed order (SPEC § 6.1). Only `auto`/`mda` sort by dependency.
