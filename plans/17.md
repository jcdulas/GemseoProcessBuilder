# 17 — Runner and run manager

Status: Done
Depends on: 16
SPEC: § 11.1, § 11.2, § 11.3, § 11.4, § 12.1 (run folder), § 17 (risk 2)

## Goal

Execute a driver from the UI in a separate process that runs the generated script, streams structured events, and can be stopped cleanly or killed.

## Scope

In:
- Runner entry point `python -m gemseo_process_builder.runner <run_dir>`: loads `script.py` and `script.gpb-map.json` from the run folder, calls `build_scenario()` (or `build_mda()`), attaches instrumentation, executes, saves outputs, emits `finished`.
- Event channel on the protected stdout (reuse `workers/protocol.EventChannel`), commands on stdin (`stop`).
- Instrumentation:
  - `Database` new-iteration listener → `iteration` (optimization) or `sample` (DOE) + `progress`;
  - discipline execution status → `status { node_id, state }`: first check GEMSEO 6's status observation API; fall back to wrapping `execute` on each discipline instance; record which one was used;
  - logging handler → `log` events;
  - rate limiting (20 messages/s per type, aggregation beyond).
- Stop protocol: `stop` on stdin → a flag checked in the listeners → raise a `RunStopped` exception → partial history saved → `finished { state: "stopped" }`. After `stop_timeout_s` without `finished`, the UI kills the process tree with psutil.
- Run manager in the UI process:
  - launch sequence of § 11.1 (validation, project snapshot, script generation, dry run, `QProcess` start);
  - run folder creation `<project>.runs/<run_id>/` with `run.json` (status updated at each stage), `project.gpb.json`, `script.py`, `script.gpb-map.json`, `run.log`;
  - one run at a time unless the preference allows concurrency;
  - lock of the running driver's configuration (commands touching it are rejected with a clear message);
  - bridge methods `run.start`, `run.stop`, events `run.started`, `run.event`, `run.log`, `run.finished`.
- Toolbar and Run menu actions (Run F5, Stop Shift+F5) enabled with proper states.

Out:
- UI monitoring widgets (plan 18), results reading and Runs panel (plan 19).

## Design

- Run ids: `r-YYYYMMDD-HHMMSS[-n]`.
- Contract with the generated script (SPEC § 10.1, plan 16): the runner imports the module, calls `build_scenario()`, attaches its instrumentation, calls `execute_scenario(scenario)`, then saves `history.h5` and `dataset.csv` itself into the run folder. It never calls `main()`.
- Killing: `psutil.Process(pid).children(recursive=True)` then terminate/kill, on Windows and Linux.
- `run.json` statuses: `preparing | running | completed | stopped | failed | killed`.

## Implementation notes

- Runner (`python -m gemseo_process_builder.runner <run folder>`):
  - It imports `script.py` and reads `script.gpb-map.json`. It calls `build_scenario()` and `execute_scenario()`, or `build_process()` then `execute()` (the outputs go to `results.json`), and never `main()`.
  - Events go out on the protected stdout (`EventChannel`, reused from the worker): `started`, `log`, `status`, `progress`, `iteration`, `sample`, `batch`, `finished`.
  - `prepare_gemseo()` enables GEMSEO's discipline status, and removes GEMSEO's stream handlers because `log` events already carry its log. It does nothing when the script does not import GEMSEO (protocol tests).
- Instrumentation, decided and written into SPEC § 11.3:
  - GEMSEO 6's `execution_status.add_observer` with `configure(enable_discipline_status=True)`, so no `execute` wrapper;
  - a `Database.add_new_iter_listener` whose point *k* is reported when point *k+1* starts, because constraints are not computed yet when the listener fires;
  - the iteration payload has x per variable, f, g (inequalities), h (equalities), observables and `feasible` (GEMSEO's default tolerances); samples have inputs and outputs;
  - `progress.total` comes from the sidecar (`max_iter`, `n_samples`, or the size of the parametric grid).
- Rate limiting: `runner/rate_limiter.py` sends up to 20 events per second per type. The rest go out as one `batch {event, items}` in the next window, or on the flush every 0.5 s. Waiting statuses keep only the latest per node, and batches are capped at 200 items with a `dropped` count.
- Stop:
  - `runner/stop.py` has a reader thread that sets a flag on `{"command": "stop"}`, or when stdin closes (the app went away).
  - Listeners and status observers check the flag and raise `RunStopped`, which GEMSEO lets through. The partial history is saved and `finished {state: stopped}` is sent.
  - `scenario.to_dataset()` took 32 s on a stopped 9,157-sample DOE, so the runner writes `database.to_dataset()` instead (0.02 s).
- `RunManager` (`app/run_manager.py`):
  - launch sequence: static validation (errors in the target subtree refuse the run), then the run folder `<project>.runs/r-YYYYMMDD-HHMMSS[-n]/` (or `settings.runs_dir`) with `project.gpb.json`, `script.py`, `script.gpb-map.json`, `run.json` and `run.log`, then an asynchronous dry run in the worker, then `QProcess` (same PYTHONPATH as the worker);
  - one run at a time unless `allow_concurrent_runs`;
  - `run.json` status goes `preparing | running | completed | stopped | failed | killed`;
  - stop, then kill of the process tree with psutil after `stop_timeout_s`;
  - `stop_all()` when the app closes.
- Locking: `Document.locked` (node id → reason) is checked after each command, undo and redo. A change touching a locked node is reverted and refused ("Study is running: stop the run before changing it."). Layout changes stay allowed. The run locks its driver and all its descendants.
- Bridge: `run.start {target?}` (the first top-level driver by default), `run.stop {run_id?}`, `run.state`. Events are `run.started`, `run.updated`, `run.event`, `run.log` and `run.finished`.
- Page (`shell/run.js`):
  - F5 runs the selected driver, or the driver around the selection, or the driver shown, or the first top-level driver. Shift+F5 stops.
  - Run and Stop are enabled according to the active runs.
  - The status bar shows "Study: running…/stopped…", with colors.
  - Failures open an error dialog.
  - Run logs appear in the Console with the `[run]` source (sources now follow the logger: app, worker, run).
- Tests:
  - rate limiter with a fake clock;
  - runner protocol with a fake script as a real subprocess without GEMSEO (completed, stop, closed stdin, failure, stdout protection), about 0.1 s each;
  - instrumentation in-process on Sellar MDF, 3 iterations (iteration and status events, stop through GEMSEO);
  - `RunManager` against a fake runner (statuses in `run.json`, stop, kill after timeout, crash, failed dry run, driver lock, refused runs).
  - `types-psutil` is added to the dev dependencies.
- Smoke-tested in the app:
  - F5 on Sellar MDF completes (`f_opt = 3.18339`), logs appear in the Console and the run folder is complete;
  - on a 200,000-sample LHS, editing the driver during the run is refused;
  - Shift+F5 stops the run within a few seconds, with status `stopped`, a partial `history.h5` (35 MB) and `dataset.csv`.
