## Goal

The foundations of the Claude copilot, without any network access yet: the `gemseo_claude_pilot` package in the repository, the protocol every backend follows, a fake backend that replays scripted answers, and the pure parts of the pilot (decisions, guardrails, detectors, context of a call with its data levels). Later plans build the segment loop (58), the real backends (59) and the application integration (60–63) on top of them.

## Scope

In, in `plugins/gemseo_claude_pilot/`:
- `pyproject.toml`: package `gemseo-claude-pilot`, MIT, Python ≥ 3.12, dependencies `gemseo>=6,<7`, `pydantic>=2`, `numpy`; no `anthropic`, `claude-agent-sdk` or `keyring` yet;
- `decisions.py`: Pydantic models of a decision and of each action (§ 4.3, 4.5), with the JSON schema used as the `submit_decision` tool input;
- `guardrails.py`: validation of a decision against the original bounds, the evaluation budget, the algorithm's compatibility with the problem and its GEMSEO settings model; clipping to the remaining budget; an error message meant to be sent back to Claude;
- `detectors.py`: the six event detectors of § 4.2, as pure functions of a history, with their thresholds as settings;
- `context.py`: a snapshot of a problem and its history (`ProblemSnapshot`, `HistorySnapshot`), extracted from a GEMSEO `OptimizationProblem`, and the text/JSON context of a call built from it (§ 6.1), including the compression of the history and the summary of large design spaces;
- `privacy.py`: the `full`, `no_code` and `anonymized` levels (§ 7.1), with the anonymization mapping and its inverse for decisions;
- `backends/base.py`: the `Backend` protocol (a conversation with tools in, text, tool calls and token usage out) and the backend errors (timeout, rate limit, authentication, other);
- `backends/fake.py`: `FakeBackend`, which replays a script of answers (text, tool calls, decisions, errors, delays) and records the requests it received;
- `prompts/`: the first system prompt, in English, versioned;
- `tests/`: pytest tests of all the above.

In, in the repository:
- `tools/check.py`, `pyproject.toml` (root): ruff, mypy and pytest cover the plugin;
- `plans/00.md` or the developer guide: installing the plugin in the venv in editable mode;
- `THIRD_PARTY_NOTICES.md`: nothing new (no new dependency).

Out:
- `ClaudePilot`, segments, warm start and the journal (plan 58).
- The API key and Claude Code backends, keyring, retries, budget, pricing (plan 59).
- The read-only tools of § 6.3 that need a running problem (`get_iterations`, …): only their schemas here; their answers come with the pilot (plan 58).
- Runner, codegen, UI (plans 60–62). DOE, BiLevel and surrogates (plan 63).

## Implementation notes

- **Layout**: three modules more than the spec listed, added to its § 3.1:
  - `snapshots.py`: `ProblemSnapshot` and `HistorySnapshot`, read from a GEMSEO `OptimizationProblem`; detectors, guardrails and context only work on them;
  - `algorithms.py`: the installed GEMSEO algorithms and their capabilities, read from GEMSEO (the package does not import the application, whose `workers/algorithms_methods.py` does the same);
  - `exchange.py`: one exchange with Claude (context, read tools, decision, one correction), used by the pilot of plan 58.
- **Names**: exceptions end with `Error` (ruff N818): `RejectedDecisionError`, `BackendError`, `BackendTimeoutError`, `RateLimitError`, `AuthenticationError`. `ClaudePilot` is not exported yet (plan 58).
- **GEMSEO 6.3**, found while writing the snapshots and the guardrails:
  - a maximized objective is stored as `-obj` in the database; `problem.objective_name` gives the user's name. The history keeps the user's sign; detectors work on the standardized objective;
  - constraints are stored standardized (`-[c_2-1.0]` for `c_2 >= 1`); `function.original_name` gives the user's name. The context gives standardized values and says so;
  - `Database.get_iteration` does not take an index: the best entry is read with `islice(database.items(), index, None)`;
  - DOE algorithm descriptions have no capabilities (`getattr(..., False)`), and their settings require `n_samples`, added before validation;
  - settings models forbid unknown fields, so a typo of Claude is refused with GEMSEO's message;
  - COBYLA is `NLOPT_COBYLA`.
- **Guardrails**:
  - settings the pilot owns are refused (`use_database`, `store_jacobian`, `reset_iteration_counters`, progress bar and logging settings, `callbacks`, `preprocessors`);
  - `max_iter` is clipped to the evaluations left, as if an iteration were an evaluation, until open point 1 is settled in plan 58; a switch of algorithm always gets `max_iter`;
  - a starting value outside new bounds is moved into them, with a note; a DOE region has no starting value.
- **Anonymized level**: equalities are `h1…` and observables `o1…`, next to `x`, `f`, `g`. Design values are normalized by the bounds the user set, for the whole run (the anonymizer keeps them); the objective and each constraint are divided by their first nonzero magnitude, fixed for the run, so constraints keep their sign. Tolerances, components and the values of past decisions are not sent. Decisions come back with values normalized per component, or one value for all. The spec's § 7.1 says so.
- **Context**: variables of at most 10 components are listed when the design vector has at most 200; otherwise each variable is summarized (bounds, best point, share at each bound) and the 20 most important components are given, ranked by gradient times range, or by normalized move since the first point without gradient. The history is compressed by doubling the windows, then halving the recent evaluations, down to 5. On 100,000 variables, snapshot and context take about 20 ms.
- **Tests**:
  - instead of Rosenbrock, the snapshots are tested on Sellar (minimized and maximized) and on a problem built by hand with 100,000 variables; the compression on 5,000 evaluations with a 3,000-token target;
  - the plugin tests have their own `conftest.py`: it imports GEMSEO and solves the Sellar scenarios the tests read, at collection time. Solving one in a test once exceeded the one-second limit while GEMSEO started the threads of its MDA;
  - the root `pyproject.toml` puts the plugin's `src` and `tests` on pytest's path, so the tests also run without installing it; mypy checks the plugin; ruff treats it as first-party and does not require docstrings in its tests. The CI installs the plugin in editable mode.
- **Formatting**: `ruff format` also formats the Python blocks of Markdown files; the example of the spec's § 8 was reformatted.
