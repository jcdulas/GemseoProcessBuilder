# 28 — Executable wrapper runtime

Status: Done
Depends on: 14
SPEC: § 7.5 (configuration), § 7.6 (descriptors), § 17 (risk 1)

## Goal

Provide a GEMSEO discipline that wraps an external executable through input file templates and output parsing rules (the Quick Wrap / File Wrapper equivalent), usable from generated scripts, with a reusable descriptor format.

## Scope

In:
- Study GEMSEO 6's executable-discipline base class (if any): decide whether `ExecutableDiscipline` subclasses it or is standalone; record the decision in the notes and SPEC § 17 risk 1.
- `runtime/executable.py`:
  - `ExecutableDiscipline(Discipline)` built from an `ExecutableSpec` (Pydantic);
  - command with tokens (`{input_file}`, `{output_file}`, `{workdir}`), environment variables, timeout;
  - working directory policy: one temporary folder per execution (unique, safe with `n_processes > 1`), retention `always | on_error | never`, files to copy in;
  - input templates with `{{variable}}` and `{{variable:format}}` markers, scalars and vectors (vector rendering configurable: separator, one per line);
  - output rules: `regex`, `marker` (line after a marker, column n), `key=value`, `table` (block → vector), `file` (path of a produced file);
  - error handling: expected return codes, error patterns in stdout/stderr, clear exception messages naming the rule that failed;
  - logging of the command, duration and working directory.
- Descriptor file `*.gpbwrap.json` = serialized `ExecutableSpec` + ports metadata (units, descriptions); load/save helpers.
- Catalog: descriptors found in plan 09 become droppable components of kind `executable`; introspection reads ports from the descriptor.
- Codegen: `ExecutableDiscipline.from_descriptor("path/to/wrapper.gpbwrap.json")` when the component comes from a descriptor; inline `ExecutableSpec(...)` otherwise (readable, one argument per line). Import from `gemseo_process_builder.runtime`.
- Example `examples/external_code/`: a tiny Python "solver" script with input/output files, its descriptor and a project using it.

Out:
- The graphical wrapper editor (plan 29).

## Design

- Template rendering and output parsing are pure functions with thorough unit tests; only one or two tests actually spawn the tiny solver (each must stay under one second: the solver must not import heavy libraries).
- Paths in descriptors are relative to the descriptor file.

## Implementation notes

- Decision (SPEC § 7.5, § 17 risk 1): GEMSEO 6.3 has a public `DiscFromExe`, which handles one template in its own `GEMSEO_INPUT{…}` syntax and parses by templates, and private base classes (`_BaseDiscFromExe`, `_BaseExecutableRunner`). `ExecutableDiscipline` derives from the public `Discipline` instead, so it relies on no private API.
- `runtime/spec.py` (Pydantic only; the UI reads descriptors without GEMSEO):
  - `ExecutableSpec`: command, inputs and outputs (`PortSpec`), templates, rules, `input_file` / `output_file`, files to copy, environment, timeout, return codes, error patterns, `workdir_root`, `retention`, `vector_separator`.
  - Output rules form a union on `kind`: `regex` (first / last / all), `marker` (line offset, column), `key_value`, `table` (until an end marker or an empty line), `file`. The file `stdout` reads the standard output.
  - `load_descriptor` returns the spec and the descriptor's folder, which relative paths refer to. `save_descriptor` / `spec_data` leave defaults out but keep each rule's `kind`.
- `runtime/templates.py` (pure): `{{x}}` and `{{x:.6e}}` markers, vectors joined by the separator, `\{{` escapes a marker; errors for missing inputs and bad formats.
- `runtime/parsing.py` (pure): numbers in Fortran notation too; each error names the rule, its variable, its file and what was missing.
- `runtime/executable.py`:
  - Each run gets its own `mkdtemp` working folder (safe in parallel). It copies files, renders the templates and runs the command in a shell. Tokens: `{python}`, `{workdir}`, `{input_file}`, `{output_file}`.
  - On timeout, the process tree is killed with psutil: with `shell=True`, killing the shell alone would leave the code running and holding the pipes on Windows.
  - Then it checks return codes and error patterns and reads the outputs.
  - Retention: `on_error` by default, so failed folders are kept and named in the error.
  - The command, the duration and the folder are logged.
  - `ExecutableDiscipline.from_descriptor(path)`.
  - Internal methods are `_write_inputs` / `_run_command`: `_execute` would override GEMSEO's own method.
- Integration:
  - The worker introspects executable components from their spec (ports, defaults, units, descriptions); `executable` joined the introspected kinds (Python and JS).
  - The inspector edits the descriptor path, with a file dialog.
  - Catalog descriptors already became executable components (plan 09).
- Codegen:
  - With a descriptor: `SOLVER_WRAPPER = Path(...)` and `ExecutableDiscipline.from_descriptor(SOLVER_WRAPPER)`. Otherwise, an inline `ExecutableSpec(...)`, with a `base_folder` constant when given.
  - Always `set_jacobian_approximation()`, with a comment: external codes give no derivatives.
  - The golden `external_code.py` uses a relative descriptor path, so it is the same on every machine.
- Example `examples/external_code/`: `solver.py` (standard library only), `input.tmpl`, `solver.gpbwrap.json` (key=value rules, `Traceback` error pattern, timeout 30 s) and `external_code.gpb.json` (SLSQP on x, y minimizing f subject to g ≤ 0; built by `tools/build_examples.py`).
- Tests:
  - templates and parsing;
  - executions with the example solver, `exit 3`, `echo` of an error pattern, a missing output file, output read from stdout with retention "always", and a timeout of 0.3 s;
  - descriptor round trip, introspection, and a dry run of the example.
- Smoke-tested:
  - Run from the UI, the example reaches f = 1.125 at (0.75, 1.75), the expected constrained optimum.
  - The exported script, run standalone from another folder, reaches the same optimum and leaves no working folder behind.
