# 16 — Scenario code generation and dry run

Status: Done
Depends on: 15
SPEC: § 6.2, § 9.2, § 10, § 15.3

## Goal

Generate readable scripts for DOE, Optimization and Parametric study drivers with the MDF, IDF and DisciplinaryOpt formulations, and validate them with a dry run in the worker before any execution.

## Scope

In:
- Codegen for:
  - design space (`create_design_space`, one `add_variable` per variable);
  - `MDOScenario` with objectives (min/max), constraints (type, operator, threshold → GEMSEO `value` / `positive` arguments), observables;
  - `DOEScenario` with responses (objective + observables), `n_samples`, `n_processes`;
  - parametric study as a DOE (`fullfact` or `CustomDOE` with the level grid);
  - formulation name and settings, algorithm name and settings (only non-default values).
- Script contract (SPEC § 10.1): `build_scenario()` builds everything, `execute_scenario(scenario)` runs the algorithm with its settings, and `main()` calls both then saves `history.h5` and `dataset.csv` next to the script. The runner (plan 17) calls `build_scenario()` and `execute_scenario()` and saves the outputs itself.
- Dry run: worker method `codegen.dry_run(source)` imports the generated module from a temporary file and calls `build_scenario()` without executing; GEMSEO exceptions are mapped back to nodes through the mapping sidecar and to the driver when unmapped. Shown in Problems with the `dry_run` source tag.
- `Model › Validate` (F7) now runs the static validation, then the dry run.
- Reference projects in `examples/`: Sellar MDF, Sellar IDF, Sellar DisciplinaryOpt, Rosenbrock DOE (LHS), Rosenbrock parametric study.
- Golden scripts for each, with lint/type checks (reuse plan 14 tests).

Out:
- Running from the UI (plan 17), BiLevel and nested drivers (plan 23).

## Design

- The example of SPEC § 10.3 is the style reference. Verify each GEMSEO call against the installed 6.x version and update SPEC § 10.3 if an argument name differs.
- Constraint translation: `operator ">="` with value `v` → GEMSEO `positive=True, value=v`; `"<="` → default. Explain with a short comment only when `positive=True` is used.
- Test settings are reduced (`max_iter=5`, `n_samples=10`) in the test copies of the examples so equivalence tests stay under one second; the example files themselves keep realistic settings.

## Implementation notes

- `codegen/design_space.py`: `build_design_space()` has one `add_variable` per design variable.
  - Bounds and values are written as a single number when all elements are equal, keeping the typed text; otherwise as a list.
  - Missing bounds are left out, and `type_="integer"` is written for integer variables.
  - Parametric studies get one variable per level, bounded by the extreme values.
- `codegen/scenarios.py`: `build_scenario()` calls `create_scenario(build_disciplines(), objective, build_design_space(), name=…, [scenario_type="DOE"], [maximize_objective=True], formulation_name=…, **formulation settings)`.
  - One `add_constraint` per constraint. `constraint_type` is always written, because GEMSEO's default is `"eq"`. `>=` becomes `positive=True`, explained once in a comment.
  - For DOEs, the first response is the objective and the others are observables.
  - `execute_scenario(scenario)` passes only non-default settings. A DOE gets `n_processes` from the Execution tab. A parametric study runs `CustomDOE` with `build_samples()` (`array(list(product(x_values, y_values)))`, using `linspace` or explicit lists).
  - `main()` saves `history.h5` (if enabled) and `dataset.csv` next to the script.
  - GEMSEO has no full factorial DOE without pyDOE, hence `CustomDOE`.
  - Mixed objective senses are refused with a clear `CodegenError`.
- Formulation comments: MDF names the coupling loop, IDF says the optimizer sets the couplings, DisciplinaryOpt says the disciplines are chained. They say "at each iteration" or "for each sample".
- Two GEMSEO 6.3 findings, written into SPEC § 10.3:
  - **Typed values** now go on the disciplines themselves (`default_input_data.update({...})`), on *every* discipline using the variable (a typed value belongs to the global variable). `main()` of process targets therefore calls `execute()` without arguments. Design variables keep the design space value.
  - **`RemappingDiscipline._compute_jacobian`** passes the new input names to the wrapped discipline (`KeyError`). A remapping that renames inputs therefore gets `set_jacobian_approximation()`, with a one-line explanation.
- IDF needs the coupling variables in the design space (GEMSEO default `include_weak_coupling_targets=True`):
  - `DriverVariables.couplings` lists them, and the picker offers them under IDF;
  - `design_variable_not_free` accepts them;
  - a new `idf_missing_couplings` rule lists the missing ones.
- The default formulation of parametric studies is DisciplinaryOpt.
- Dry run:
  - The worker method `codegen.dry_run(source, mapping)` imports the script from a temporary file and calls `build_scenario()` or `build_process()` without executing.
  - An error is attached to the component whose variable starts the failing line of the script: the sidecar now includes `variables: {python variable: node id}`. Other errors go to the target.
  - `validation.dryRun` runs every top-level driver (or the model), reports `codegen` or `dry_run` errors, and clears them at the next change.
  - F7 runs the static validation, then the dry run ("Dry run…" in the status bar).
- Examples:
  - `examples/`: `sellar_mdf`, `sellar_idf` (with `y_1` and `y_2` as design variables), `sellar_disciplinary_opt` (an MDA assembly under the optimizer), `rosenbrock_doe` (LHS, 30 samples, seed 1) and `rosenbrock_parametric` (5 × 3 grid). `tools/build_examples.py` recreates them.
  - The five examples are golden scripts, checked by ruff and `mypy --strict`.
- Equivalence tests import the generated script and run it against hand-written GEMSEO: Sellar MDF, IDF and DisciplinaryOpt with SLSQP `max_iter=2` (same optimum and x within 1e-8), Rosenbrock LHS with 10 samples (identical dataset), and the parametric grid checked against the formula. Each test takes under 0.25 s.
- Checked by hand: the five exported scripts run standalone. MDF, IDF and DisciplinaryOpt all reach the Sellar optimum, 3.18339. In the app, F7 on a valid project reports nothing. `init_args` `{bogus: 1}` on Sellar1 gives "Dry run of Optimizer: TypeError: …" attached to `Model.Optimizer.Sellar1`.
- UI fixes:
  - the status bar has a `validation` slot;
  - form rows use `minmax(0, 1fr)`, so the inspector no longer scrolls horizontally.
