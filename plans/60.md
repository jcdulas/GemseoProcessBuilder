# 60 — Copilot in the runner

Status: Done
Depends on: 59
SPEC: [CLAUDE_PILOT_SPEC.md](../docs/CLAUDE_PILOT_SPEC.md) § 4.1, 8, 9.1, 10.2, 10.3; SPEC § 1.2, 10, 11.2, 12.1

## Goal

A driver of the application can be piloted: its configuration holds the copilot's settings, the generated script runs it through `ClaudePilot` in a few readable lines and is read back into the same settings, and a run started from the application reports what the copilot does and accepts its commands, which makes the Advisor mode possible.

## Scope

In, in the plugin:
- `events.py`: the channel between the pilot and the process running it: events published (status, messages, proposals, decisions, usage, segments, summary), commands received (accept, reject, mode);
- `pilot.py`: the Advisor mode when a runner listens (proposals accepted or rejected by the user, replaced by newer ones, expired), the mode changed during the run, the events;
- `journal.py`: its folder is created at the first record, not before;
- `py.typed`, so that the generated scripts are type-checked against the plugin.

In, in the application:
- `core/drivers.py`: `Copilot` settings of a driver (enabled, mode, allowed actions, data level, calls of the budget);
- codegen: `execute_scenario` of a piloted optimization driver;
- script reader: the pilot of a script read back into the driver's settings, without running it;
- static validation: the copilot only pilots an optimization driver run on its own;
- runner: the journal in `copilot/` of the run folder, the pilot's events on the event channel, the copilot commands passed to it, its summary in `run.json`;
- run manager and bridge: `run.copilot(run_id, command, params)` writes a command to the runner;
- SPEC.md: § 1.2, § 10, § 11.2, § 12.1.

Out:
- The preferences, the Copilot tab of the driver editor, the Copilot panel (plan 61). Questions from the chat (plan 62). DOE, BiLevel (plan 63).

## Implementation notes

- **Events**: `gemseo_claude_pilot.events` holds the listeners and a queue of commands; the pilot publishes, the runner subscribes. The runner never imports the plugin: `runner/copilot.py` subscribes only when the script imported `gemseo_claude_pilot.events` (every piloted script does, through `ClaudePilot`). `copilot.status` and `copilot.usage` go through the rate limiter keeping the latest; the other copilot events are sent at once. Event names follow the channel's: `copilot.segment` and `copilot.summary` rather than `segment` (spec § 10.2 updated).
- **Advisor mode**: decided when the run starts (a listener is needed), not when the pilot is built. A proposal has an id (`p1`, `p2`…); a newer one replaces it; accepted more than 50 evaluations later, it expires. When a segment ends by itself with an open proposal, the pilot waits for the answer (`answer_timeout`, 120 s), polling the commands every 0.1 s, unless the budget is spent (no segment could follow). `copilot.mode` changes the mode during the run; switching to Pilot applies the open proposal.
- **Stop**: the runner passes every command to the pilot, `stop` included, so that a pilot waiting for an answer ends; a run that ends by itself after a stop request is reported `stopped`.
- **Summary**: the pilot's `copilot.summary` is added to the summary of `finished`, outside the saving of the outputs (a run without evaluation fails to save them).
- **Codegen**: only the settings that differ from `ClaudePilot`'s defaults are written (`mode`, `allowed_actions`, `data_level`, `budget=Budget(max_calls=...)`); the comment is built from the mode and the allowed actions. `Budget` is exported by the plugin's package. The plugin has a `py.typed` marker: `mypy --strict` checks the golden script against it.
- **Reader**: `ClaudePilot.execute` is replaced while reading, like `scenario.execute`; building a `ClaudePilot` has no side effect (the journal's folder is created with its first record).
- **Tests**: both test suites set `GEMSEO_CLAUDE_PILOT_BACKEND=off`. The runner test uses a copy of the plugin's `events.py` in the run folder: importing the whole plugin in the runner process took too long for one second.
- **End to end, by hand**: the generated script of a piloted Sellar MDF (Advisor mode, 4 calls) run by the real runner with Claude Code: 3 calls in 76 s (start review, a bounds event judged a false alarm, the end), every copilot event on the channel, the summary in `finished`, the journal in `copilot/`. Claude made no proposal on this healthy run, so accepting one was only checked with the fake backend (`test_events.py`) and through the run manager with a fake runner.
