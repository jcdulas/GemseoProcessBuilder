# 04 — Project model and file format

Status: Done
Depends on: 03
SPEC: § 4, § 14.2 (autosave)

## Goal

Define the project data model as Pydantic models, read and write `.gpb.json` files with schema versioning and migrations, and wire the project lifecycle actions (new, open, save, save as, close, recent projects, autosave and recovery).

## Scope

In:
- Models for Project, Assembly, Component, Driver, Port, Link, Layout, Surrogate reference, Run reference (SPEC § 4.1, § 4.2). Driver `config` and component `config` are typed per `kind` but may stay minimal here; later plans extend them.
- Serialization: indented JSON, stable key order, relative paths, separate `layout` section.
- `schema_version` and a migration framework (with a test migration from a fake version 0).
- `project.*` bridge methods and File menu actions, native dialogs, dirty state, recent projects.
- Autosave every 2 minutes and recovery at startup.

Out:
- Editing the model (plan 05).
- Displaying it (plans 06, 07).

## Design

- Node types are a discriminated union on `type` (`assembly | component | driver`); components and drivers use a second discriminator on `kind`.
- Node names: a letter followed by letters, digits or `_` (like ModelCenter names; this also keeps codegen naming simple). Unique within a parent (model validator). Port names follow GEMSEO rules (any non-empty string without `:`, which is reserved for namespaces).
- `Port.global_name` is **not** stored when equal to `local_name` (derived; stored only when overridden — plan 11 relies on this).
- The in-memory model uses absolute paths; `serialization` converts to/from relative paths.
- `dumps()` output is deterministic: same model → byte-identical file (tests rely on it).
- Autosave writes `<project>.gpb.json.autosave` only when dirty; it is deleted on save or clean close. At startup, if an autosave is newer than its project, the UI offers "Recover" / "Discard".
- Untitled projects autosave to the user data dir.

## Implementation notes

- **Model** (`core/model.py`): `ComponentNode`, `AssemblyNode`, `DriverNode` form a discriminated union on `type`. `kind` is a plain `Literal` field; component and driver `config` are free dictionaries for now (driver configs get typed models in plan 15, component configs are validated by their editors in plan 10).
- Node names: a letter followed by letters, digits or `_`; unique among siblings. Port names: non-empty, without `:`; unique per direction (a variable may be both an input and an output of the same component, as GEMSEO allows).
- Extra `Port` fields for later plans: `default_text` (value as typed, for readable codegen), `shape_known`, `missing` (plan 10), `global_name` override (plan 11). `Link.convert_units` (plan 27). `AssemblyNode.mda_settings`, `isolated`, `transparent`.
- **Layout** is typed: `layout.nodes[id] = {x, y, collapsed, port_display}`, `layout.levels[container id] = {x, y, k}`, `layout.tree_expanded`, `layout.extra` (free-form view state). SPEC § 4.2 updated.
- **Files**: default values are omitted to keep files short and diffs readable; `schema_version`, `metadata` (creation date, app version), the root node and every node `type` are always written. Keys are sorted; the output is byte-identical for the same project. Writes are atomic (temporary file + `os.replace`).
- **Paths**: every configuration key ending with `_path` is treated as a file path, as well as catalog folders, the runs folder, surrogate and run folders. Relative to the project folder in files, absolute in memory; paths on another Windows drive stay absolute.
- **Migrations**: `CURRENT_SCHEMA_VERSION = 1`; version 0 is the flat layout format of the first SPEC draft, which gives the migration framework a real test.
- **Project lifecycle** (`app/project_session.py`, `app/api_project.py`): the session is Qt-free; the controller asks questions through a `Dialogs` protocol (`QtDialogs` in the app, a fake in tests). `project.*` methods: `get`, `state`, `new`, `open`, `save`, `saveAs`, `close`, `recent`. Events: `project.changed` (name, path, dirty) and `document.reset` (whole document).
- "Close project" leaves an empty untitled project. A project saved for the first time takes its name from the file name.
- Autosave every 2 minutes to `<file>.autosave`, or to `untitled.gpb.json.autosave` in the application data folder for untitled projects; recovery is offered when opening a project whose autosave is newer, and at startup for an untitled autosave. Quitting after discarding changes deletes the autosave.
- File › Open recent is a native submenu handled in Python. The application accepts a project path on the command line.
- Checked in the real application: the Sellar fixture opened from the command line, title and status bar updated, `project.get` / `project.state` / `project.recent` answered.
