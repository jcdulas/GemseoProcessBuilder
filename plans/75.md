# 75 — Catalog entries from installed packages

Status: Done
Depends on: 09, 10
SPEC: § 3.4, 4.2, 4.2.1, 7.6, 9.1, 10.1, 14.5, 15.2, 17 (open point 10); [SIZING_LOOP_EVOLUTIONS.md](../docs/SIZING_LOOP_EVOLUTIONS.md) § 2 (GPB-E1)

## Goal

An installed package gives its disciplines and functions to the Library through the entry-point group `gemseo_process_builder.components`, with their descriptions and units, without a catalog folder and without depending on the application; the generated script imports them as a developer would (`from gemseo_nastran.sizing import StructuralSizing`). First user: `gemseo_nastran`. Milestone M3 of the sizing loop (ECOSYSTEM-EVOLUTIONS.md § 6).

## Scope

In:
- the owner's confirmation of the name of the group (SPEC § 17, open point 10), before any code;
- worker method `catalog.packages`: the discovery of SPEC § 7.6 (entry points listed with their distribution, importing nothing; declarations loaded; keys checked, unknown keys warned; each `module` located with `importlib.util.find_spec`, not imported); one error per package, with its traceback;
- the catalog cache keyed by (distribution name, version), plus the modification time of the declaration file for an editable install (PEP 610 `direct_url.json`); **Refresh** reloads every package;
- `catalog.list` and the event `catalog.updated` carry the packages;
- Library: one section per package after the folders ("gemseo-nastran 0.3.0"), its entries grouped by `group`; search, error rows and drag and drop as for folder entries;
- a placed component keeps its dotted `module`, its class or function and `package {name, version}` in its `config`; introspection imports the module (§ 7.3);
- codegen: one `from <module> import <attribute>` line, no `sys.path`;
- script reader: a discipline whose module belongs to a declared package records that package;
- validation: the package missing from the Python of the runs (Error), another version (Info).

Out:
- the declaration of `gemseo_nastran` (its own specification);
- `gemseo_plugins` (GEMSEO's registration, which the application does not need);
- executable descriptors and surrogates given by packages.

## Implementation notes

- Group name: the owner's request of 2026-10-12 for milestone M3 names `gemseo_process_builder.components`; SPEC § 17, open point 10 is closed with it.
- Discovery (`catalog/packages.py`, worker method `catalog.packages`): the application sends the packages of its cache (`name`, `version`, `stamp`) and `force`; the worker answers a scan per package, or `unchanged` for one whose version (and, for an editable install, the modification time of its declaration file) did not change. The entry points of one distribution make one package. The cache of the packages is a file of its own, `catalog_packages.json`, beside `catalog_cache.json` (whose format is unchanged).
- Deviation from the spec's wording: the modules are located by asking the finders of `sys.meta_path` segment by segment (`locate`), not with `importlib.util.find_spec`, which imports the parent packages; the editable stamp is found the same way. SPEC § 7.6 says so now.
- Errors: a declaration that cannot be loaded gives one error and no entry; a malformed entry or a module not found gives one error naming the entry, and the other entries of the package stay listed (`PackageScan.errors`, a list). Unknown keys and a `schema` above 1 are warnings, shown in the section and logged.
- A declaration module loaded before is popped from `sys.modules` before it is loaded again, so that an edited editable install, or a new version, is read in a running worker.
- Units: the worker reads the declaration again when it introspects a component recording a package (`declared_units`, cached until the next scan), so the units of a package entry need nothing in the project.
- The script reader records the package of a discipline whose top-level package is that of an entry of a declared package (not `importlib.metadata.packages_distributions`, which misses editable installs).
- Validation: `ValidationContext.packages` (the versions by normalized name, `None` before the first scan, when the rule stays silent); the catalog service emits `packages_changed` when the set or the versions change, and the validation runs again.
- Codegen needed no change: a dotted `module` was already generated as one import line. No golden script was added: the golden scripts are type-checked by mypy and must import installed modules; the test writes the script of a component of a fake distribution, runs it and reads it back instead.
- Checked by hand: the real worker process (`python -m gemseo_process_builder.workers.introspection`) answers `catalog.packages` for a distribution put on its `PYTHONPATH`. Not checked: the window itself, and `gemseo_nastran`, which exists only as a specification.
