# 19 — Results storage and Runs panel

Status: Done
Depends on: 17
SPEC: § 12.1, § 8.8 (Runs), § 4.2 (runs index)

## Goal

Persist every run in its folder, index runs in the project, list them in the Runs panel, and give the UI a query API over run data that works for large results.

## Scope

In:
- Run folder layout of SPEC § 12.1 finalized; `run.json` schema (Pydantic, versioned): driver id and path, dates, duration, status, GEMSEO and app versions, summary (best objective, feasibility, number of evaluations), variable metadata (names, sizes, roles).
- Project `runs` index updated on run start/finish (not an undoable command; marks the project dirty).
- Results reading in the worker (HDF5 needs GEMSEO/h5py, which the UI process must not import): methods `results.summary(run)`, `results.columns(run)`, `results.rows(run, offset, limit, sort, filter)`, `results.history(run, variables)`, `results.export_csv(run, path, columns)`.
- Runs panel: table (id, name, driver, date, duration, status, best objective), rename (display name in `run.json`), delete with confirmation, open (opens the Results tab — placeholder until plan 20), reveal folder, "Export CSV…".
- Orphan handling: folders on disk not in the index are offered for re-import; index entries without a folder are flagged.
- Summary computed at the end of a run by the runner and stored in `run.json`.

Out:
- Result charts and table views (plans 20, 21).

## Design

- Paging: `rows` returns at most `limit` rows (default 500) with the total count; sorting and filtering are done in the worker with numpy on the loaded arrays (cached per run in the worker, LRU of 3 runs).
- Filter expressions are structured (`[{ column, op, value }]`), never evaluated strings.
- Deleting a run removes its folder only after the index update succeeds; failures are reported.

## Implementation notes

- `results/models.py` holds the versioned `run.json` (`RunInfo`, `schema_version = 1`; unknown keys are ignored so older and newer runs stay readable):
  - driver id, driver name and path (`Model.Optimizer`), display name, dates, duration, status, pid, error;
  - versions of the app, Python and GEMSEO;
  - `RunSummary` (evaluations, objective name, best objective, feasibility, x_opt per variable, outputs of a process run);
  - `VariableInfo` (name, size, role, constraint type).
  - `read_info` and `write_info` (atomic, through a temporary file) live here, without Qt, because the worker uses them.
- The runner writes the summary at the end: evaluations from the database, and the optimum from `optimization_result` when there is one. It also sends the variables with their roles (DOE outputs are `output`), constraint types and versions. `RunManager` builds `run.json` from `RunInfo` and indexes the run as soon as it starts.
- `results/store.py` (`RunStore`, app side):
  - The runs folder is `settings.runs_dir`, or `<project>.runs` next to the project.
  - The `Project.runs` index uses paths relative to the project folder. It changes outside the undo history and only marks the project dirty; project changes cannot carry lists to the page, and the page queries runs through the bridge anyway.
  - Entries flag missing folders. Orphans are run folders with a readable `run.json` that are not indexed; they can be imported, and missing entries can be forgotten.
  - `rename` changes the display name in `run.json`. `delete` updates the index first, then removes the folder and reports a failure.
- `results/reader.py` (worker side, NumPy):
  - It reads `dataset.csv` (the GEMSEO dataset's 3-line header). Columns are `x_shared[1]`-style names with the roles of `run.json`, plus `evaluation` first and a computed `feasible` column (GEMSEO's default tolerances) when there are constraints.
  - `rows` pages with a total, a stable sort (NaN last) and structured `Filter` objects (`<`, `<=`, `>`, `>=`, `==`, `!=`, `between`; nothing is evaluated). `history` returns columns, `export_csv` writes one header line, and `summary` returns `run.json` with the size.
  - An LRU cache keeps 3 runs, keyed by folder and modification times.
- `workers/results_methods.py` provides `results.summary/columns/rows/history/export_csv`.
- `app/api_results.py`:
  - `runs.list` (entries and orphans), `runs.folder`, `runs.rename`, `runs.delete`, `runs.importOrphans`, `runs.forgetMissing`, `runs.reveal` (file manager), `runs.exportCsv`;
  - `results.*` forwarded to the worker, in the background;
  - a `runs.changed` event.
- A native file dialog must run on the Qt thread, so the page first calls a new `dialog.saveFile`, then `runs.exportCsv` with the path.
- Runs panel (`panels/runs.js`):
  - a table, latest first: name (editable), driver path, date, duration, status, evaluations and best objective, plus Open, Folder, CSV and Delete (with confirmation);
  - a notice to add orphan folders or forget missing runs, and a count badge on the tab.
  - "Open" shows a summary tab with Export CSV until plan 20.
- Fixture: `tests/python/results/fixtures/sellar_run` (`run.json` and `dataset.csv`), produced once by the real runner on Sellar MDF with 3 iterations.
- Tests: reader (roles, paging, sort, filters, history, CSV, missing results) and store (index, rename, delete, orphans both ways, runs kept after save and reopen, unknown keys).
- Smoke-tested in two sessions: F5 on Sellar MDF, save, restart. The Runs panel lists the run (Model.Optimizer, 0:02, completed, 8 evaluations, 3.18339), and "Export CSV" writes `evaluation,x_1,…,obj,feasible`.
