# 19 — Results storage and Runs panel

Status: Not started
Depends on: 17
SPEC: § 12.1, § 8.8 (Runs), § 4.2 (runs index)

## Goal

Persist every run in its folder, index runs in the project, list them in the Runs panel, and give the UI a query API over run data that works for large results.

## Scope

In:
- Run folder layout of SPEC § 12.1 finalized; `run.json` schema (Pydantic, versioned): driver id and path, dates, duration, status, GEMSEO and app versions, summary (best objective, feasibility, number of evaluations), variable metadata (names, sizes, roles).
- Project `runs` index updated on run start/finish (not an undoable command; marks the project dirty).
- Results reading in the worker (HDF5 needs GEMSEO/h5py, which the UI process must not import): methods `results.summary(run)`, `results.columns(run)`, `results.rows(run, offset, limit, sort, filter)`, `results.history(run, variables)`, `results.export_csv(run, path, columns)`.
- Runs panel: table (id, name, driver, date, duration, status, best objective), rename (display name in `run.json`), delete with confirmation, open (opens the Results tab — placeholder until plan 20), reveal folder, "Export CSV…".
- Orphan handling: folders on disk not in the index are offered for re-import; index entries without a folder are flagged.
- Summary computed at the end of a run by the runner and stored in `run.json`.

Out:
- Result charts and table views (plans 20, 21).

## Design

- Paging: `rows` returns at most `limit` rows (default 500) with the total count; sorting and filtering are done in the worker with numpy on the loaded arrays (cached per run in the worker, LRU of 3 runs).
- Filter expressions are structured (`[{ column, op, value }]`), never evaluated strings.
- Deleting a run removes its folder only after the index update succeeds; failures are reported.
