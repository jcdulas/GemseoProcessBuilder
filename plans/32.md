# 32 — Large-model performance

Status: Done
Depends on: 31
SPEC: § 14.1, § 15.5

## Goal

Meet the performance targets of SPEC § 14.1 on the 2,000-component / 50,000-variable reference model, measured by reproducible benchmarks.

## Scope

In:
- Synthetic model generator `benchmarks/generate.py`: configurable number of components, ports per component, hierarchy depth (6 levels), coupling density, loops; deterministic with a seed; writes a `.gpb.json` using analytic components (no user code needed).
- Benchmarks (not tests, SPEC § 15.5), each printing a table and writing `benchmarks/results/<date>.json`:
  - project opening time (UI process, excluding GEMSEO import);
  - command round trip (bridge + patch + render) — measured in the page with `performance.now()` and reported through the bridge;
  - static validation full pass;
  - resolver full pass;
  - canvas pan/zoom fps on a 300-node level (scripted zoom sequence in the page, fps from `requestAnimationFrame` timings);
  - N2 2,000 × 2,000 scrolling fps;
  - auto-layout of a 300-node level;
  - results views with 50,000 samples.
- A `benchmarks/run.py` launching the app in a benchmark mode (`--benchmark <name>`) that loads the model, runs the scripted scenario and exits.
- Optimizations as needed, in priority order:
  - viewport culling on the canvas (nodes and links outside the view are not in the DOM);
  - level of detail (ports hidden, labels simplified below zoom thresholds);
  - patch batching and render scheduling (one render per animation frame);
  - resolver and validation incremental paths, profiling with `cProfile`;
  - JSON payload size (avoid sending the full document; compress large results pages);
  - virtualization audit of all lists and tables.
- Guard tests (under one second) for the pure parts that regressed or were optimized (e.g. resolver on a 300-component model < 200 ms, culling computations).

Out:
- Changing the "SVG only" constraint. If a target is still missed after optimization, document the measurement and discuss it with the user (SPEC § 17 risk 6) instead of switching to canvas rendering.

## Implementation notes

- Final measurements on the reference model: 2,000 analytic components, 50,000 variables, 6 levels, a 300-component level, and a run of 50,000 samples. Machine: Windows 11, Intel 12 threads, Qt WebEngine 6.11.2, idle. Baseline: `benchmarks/results/2026-09-25_073103.json`; final: `2026-09-25_090930.json`.

| Measure (SPEC § 14.1) | Target | Baseline | Final |
|---|---|---|---|
| Project opening, until drawn | < 3 s | 1.9 s | 1.8 s |
| Editing command, round trip + render, p95 | < 100 ms | 4,090 ms | 37 ms (median 24 ms) |
| Full static validation, Python (resolve + rules) | < 1 s | 0.82 s | 0.92 s |
| Full static validation, from the page | < 1 s | 2.1 s | 0.34 s |
| Canvas zoom, 300-node level | ≥ 30 fps | 2.9 fps | 41 fps |
| Canvas pan, 300-node level | ≥ 30 fps | 0.8 fps | 57 fps |
| N2 2,000 × 2,000 scrolling | ≥ 30 fps | 60 fps | 58 fps |
| Auto-layout of 300 nodes | < 2 s, UI not blocked | 9.8 s, frames up to 683 ms | 1.6 s, frames ≤ 33 ms |
| Results views, 50,000 samples (table / scatter / parallel / XY) | — | not drawn | 0.3 / 1.2 / 0.3 / 0.3 s |

  - Every target is met. The Python validation has little margin (0.87 to 0.92 s depending on the run): the resolution takes 0.53 s of it. An incremental resolution is the next step if models grow.
- Tools:
  - `benchmarks/generate.py` makes deterministic synthetic models (settings: components, variables per component, depth, size of the big level, coupling and loop shares, samples, seed). Duplicate inputs are replaced by free inputs, so the variable count is exact.
  - `benchmarks/run.py` prints the targets table and writes `benchmarks/results/<date>.json`; `benchmarks/README.md` explains it.
  - Benchmark mode: `--benchmark SCENARIO --benchmark-output FILE`. The page opens the project itself and runs `services/benchmark.js`. In this mode, dialogs are answered without the user (`UnattendedDialogs`: unsaved changes discarded, no recovery): a benchmark must never wait.
- Optimizations, in the order they were found by measuring:
  - Problems panel virtualized (`VirtualList`). It rebuilt 15,548 rows on every change of the document.
  - `validation.run` returns the counts only; the list reaches the page once, through `validation.updated` (3 MB on the reference model).
  - The document counts model revisions (`Document.model_rev`). Commands changing only descriptions (`Effect.cosmetic`) or only the view do not advance it. The resolution cache and the validation debounce follow it, and `resolution.updated` is emitted only when it changes. The canvas asks for couplings on that event, on reset, or when the levels to resolve change (a container expanded), no longer after every patch.
  - `buildScene`: the set of free inputs was rebuilt for each node, 100 ms for 300 nodes; it is now built once per view (5 ms).
  - Viewport culling (`lib/viewport_cull.js`, pure). Only the items near the view (drawn area = view + 50 % on each side) and their links are in the DOM. The canvas redraws when the view leaves the drawn area or the level of detail changes.
  - Level of detail: below 0.55 zoom, port labels and link counts are hidden; below 0.3, ports too. Links are painted with `optimizeSpeed` while the view moves and when zoomed out.
  - The painting of links was the main cost of the canvas. Measured on 600 links:
    - dashes: 5 fps against 18 without;
    - painted hit paths: another factor of 2.
    - Implicit couplings are now solid lines, and hit paths are `visibility: hidden` with `pointer-events: stroke`.
  - `drawScene` redraws a node only when its data (replaced by the store when touched) or what it shows changed, and a link only when its path or variables changed. A render of the fully visible 300-node level went from 104 ms to 14 ms.
  - Auto-layout of levels above 100 nodes (`LARGE_LEVEL`): nodes without ports and one edge per pair. Options: polyline routing, `SIMPLE` placement, `INTERACTIVE` crossing minimization from the current positions, no separated components. 1 to 1.6 s instead of 10 s, and a more compact layout.
- Canvas redesign, asked by the user during this plan ("a graph like n8n, and clicking a link shows the variables of both sides"; choices made: compact cards, floating panel). SPEC § 8.2 is updated. It also removes most links from large levels.
  - Nodes are cards by default (`NodeLayout.port_display` gained `compact`, now the default; `none` from older projects is drawn as a card). A card shows its header and `N in · M out` (plus the children of a container), with one link point on each side. Context menu › Variables lists the variables instead (all, or connected only), for components and containers.
  - One link per pair of nodes when one is a card, with a count badge when it carries several variables.
  - Clicking a link opens `views/canvas/link_panel.js`: outputs of the source on the left, inputs of the target on the right, with units, the kind of coupling, conversions and actions (delete an explicit link, convert, link other variables).
  - Dragging from the output point of a card onto another node opens the same panel to link variables. For each input of the target, it offers the output of the source feeding it, incompatible outputs disabled, and applies everything as one undo step. `lib/link_mapping.js` (pure, tested) computes the commands; an output with the name of an input feeds it without a link.
- Guard tests:
  - culling of 60 frames of a 300-node level with 2,000 links;
  - `buildScene` of a 300-node level with 3,600 free inputs under 60 ms;
  - large-level ELK graph;
  - link mapping;
  - model revisions of descriptions;

- Smoke-tested on Sellar MDF, driven by script:

  - the link panel (Sellar1 → SellarSystem: y_1 by name);
  - the connect panel creating an explicit link y_1 → SellarSystem.x_1, undone in one step.

- The Python validation of this model reports 15,548 "unused output" infos: the synthetic outputs are mostly unused. That is expected for the model, and it is what exposed the unvirtualized Problems panel.
