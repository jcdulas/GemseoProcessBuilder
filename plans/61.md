## Goal

The user sets the copilot up and follows it without leaving the application: the backend and its check in the preferences, the copilot of a driver in its editor, a consent before anything is sent, and, in the results of a run, what Claude says and proposes, with Accept and Reject, the mode, the usage, and the segments on the History charts.

## Scope

In:
- Preferences: backend (*Claude Code (subscription)*, the default, or *API key*), a *Check* of each, the API key stored in the OS keyring, the watch and decision models, the defaults of a new copilot (mode, data level, calls); passed to the runner in the environment.
- Worker: `copilot.status` (plugin installed, backend usable), `copilot.store_key`, `copilot.delete_key`; the worker runs the user's interpreter, like the runner, so it sees the same plugin and keyring.
- Bridge: the `copilot.*` methods, and `copilot.journal(run_id)`, the journal of a finished run.
- Driver editor: a Copilot tab for an optimization run on its own: enable, mode, allowed actions, data level with what it sends, calls of the budget, the state of the backend.
- Consent: enabling the copilot, or choosing a more open data level than the one accepted before, asks first.
- Results: a Copilot view (status, mode switch, usage, timeline, Accept and Reject on open proposals), from the live events or from the journal; segment markers on the History charts.
- Pure logic in `lib/copilot.js`, tested with `node --test`.

Out:
- The chat, the pre-run review button and the post-run report (plan 62). DOE, BiLevel (plan 63).

## Implementation notes

- **Where things run**: the check of the backend (`claude auth status`, or the key) and the keyring are in the worker (`workers/copilot_methods.py`): it runs the interpreter of the runs, so it sees the same plugin, Claude Code login and keyring as the runner; the UI process only forwards (`app/api_copilot.py`) and reads the journal of a finished run, a file of its folder. Neither the bridge nor the worker logs the parameters of a request: the API key leaves no trace.
- **Preferences**: `copilot_backend`, `copilot_watch_model`, `copilot_decision_model`, the defaults of a new copilot, and `copilot_consent`; the run manager passes the backend and the models to the runner (`GEMSEO_CLAUDE_PILOT_BACKEND`, `…_WATCH_MODEL`, `…_DECISION_MODEL`); the plugin's `Models` read them.
- **Consent**: stored in the preferences as the most open data level accepted, not in the project (spec § 7.2 updated): a project is a script, with no place for it.
- **`run.json`**: `RunSummary` ignored unknown fields, so the copilot's summary of plan 60 was dropped from `run.json`; it has a `copilot` field now. The Copilot view of a finished run reads the journal (`copilot.journal`, without the contexts sent, which are large) and the History markers the segments of that summary.
- **Checks of the backend** are kept a minute in the page: the Copilot tab is rebuilt after each change, and `claude auth status` takes a second or two.
- **Tests**: `keyring` is warmed up at collection time in the application's tests too (about two seconds the first time on Windows).
- **Not checked by hand in the application**: the page was checked by the JS syntax check and the node tests of `lib/copilot.js`, not in the running application (no scripted way to click through it). The acceptance criterion by hand (the Sellar MDF demo in Advisor mode) is to do.
