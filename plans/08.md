## Goal

Provide a long-lived **introspection worker** subprocess that runs in the user's Python environment, imports GEMSEO and user code, and answers requests over a JSON-lines protocol. The UI never imports GEMSEO.

## Scope

In:
- Shared JSON-lines protocol (`workers/protocol.py`) reused later by the runner (plan 17).
- Worker process entry point with a method registry (same style as the bridge registry).
- `WorkerClient` in the UI process: start in background at launch, request/response with futures, timeouts, cancellation, crash detection and automatic restart, `worker.status` events (`starting | ready | busy | crashed | incompatible`).
- Interpreter selection from preferences (`python_interpreter`, default `sys.executable`), with a Preferences dialog field.
- Startup handshake: the worker reports Python, GEMSEO, Pydantic and numpy versions; incompatible versions → `incompatible` status with an explicit message.
- Built-in worker methods: `worker.ping`, `worker.versions`, `worker.sleep` (tests only).
- Bridge method `worker.status` and a status bar indicator.

Out:
- Catalog scanning, introspection, XDSM, dry run, post-processing methods (their own plans).

## Design

- Messages: request `{ "id", "method", "params" }`, response `{ "id", "ok", "result" | "error" }`, event `{ "event", "payload" }`, one JSON object per line, UTF-8.
- **Stdout protection** (shared with the runner): at startup `EventChannel` duplicates file descriptor 1 for the protocol, then points fd 1 and `sys.stdout` to stderr, so prints from user code or libraries go to stderr. Stderr lines are forwarded to the Console as `worker` logs.
- Logging inside the worker goes through a handler that emits `log` events.
- Requests are processed one at a time in the worker (a single thread); long requests can be cancelled with a `cancel { id }` message checked at safe points. If a request exceeds its timeout, the client kills and restarts the worker and fails the request with `worker_unavailable`.
- GEMSEO is imported lazily by the methods that need it, right after the handshake, in the background, so `ready` is reported quickly and a `gemseo_loaded` event follows.
- The client restarts a crashed worker at most 3 times per minute, then stays in `crashed` until the user clicks "Restart worker".

## Tests

- `test_protocol.py`: encode/decode round trip, malformed lines, `EventChannel` protecting stdout (run inside a tiny subprocess that prints and emits an event; must stay under one second: no GEMSEO import).
- `test_server.py`: dispatch, unknown method, exception → error response, cancel.
- `test_worker_client.py`: against `fake_worker.py`: request/response, timeout → restart, crash → restart and status events, restart limit. Use short timeouts (≤ 200 ms).

## Acceptance criteria

- The status bar shows `Worker: ready` shortly after launch, then GEMSEO's version once loaded.
- Killing the worker process from the OS makes it restart automatically.
- Pointing the interpreter to a Python without GEMSEO shows a clear `incompatible` message.
- `python tools/check.py` passes.
