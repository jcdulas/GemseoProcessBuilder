# 08 — Worker infrastructure

Status: Done
Depends on: 02

## Goal

Provide a long-lived **introspection worker** subprocess that runs in the user's Python environment, imports GEMSEO and user code, and answers requests over a JSON-lines protocol. The UI never imports GEMSEO.

## Scope

In:
- Shared JSON-lines protocol (`workers/protocol.py`) reused later by the runner (plan 17).
- Worker process entry point with a method registry (same style as the bridge registry).
- `WorkerClient` in the UI process: start in background at launch, request/response with futures, timeouts, cancellation, crash detection and automatic restart, `worker.status` events (`starting | ready | busy | crashed | incompatible`).
- Interpreter selection from preferences (`python_interpreter`, default `sys.executable`), with a Preferences dialog field.
- Startup handshake: the worker reports Python, GEMSEO, Pydantic and numpy versions; incompatible versions → `incompatible` status with an explicit message.
- Built-in worker methods: `worker.ping`, `worker.versions`, `worker.sleep` (tests only).
- Bridge method `worker.status` and a status bar indicator.

Out:
- Catalog scanning, introspection, XDSM, dry run, post-processing methods (their own plans).

## Design

- Messages: request `{ "id", "method", "params" }`, response `{ "id", "ok", "result" | "error" }`, event `{ "event", "payload" }`, one JSON object per line, UTF-8.
- **Stdout protection** (shared with the runner): at startup `EventChannel` duplicates file descriptor 1 for the protocol, then points fd 1 and `sys.stdout` to stderr, so prints from user code or libraries go to stderr. Stderr lines are forwarded to the Console as `worker` logs.
- Logging inside the worker goes through a handler that emits `log` events.
- Requests are processed one at a time in the worker (a single thread); long requests can be cancelled with a `cancel { id }` message checked at safe points. If a request exceeds its timeout, the client kills and restarts the worker and fails the request with `worker_unavailable`.
- GEMSEO is imported lazily by the methods that need it, right after the handshake, in the background, so `ready` is reported quickly and a `gemseo_loaded` event follows.
- The client restarts a crashed worker at most 3 times per minute, then stays in `crashed` until the user clicks "Restart worker".

## Implementation notes

- **Protocol** (`workers/protocol.py`, Qt-free and GEMSEO-free): JSON lines; `EventChannel` duplicates fd 1 for the protocol and points fd 1 / `sys.stdout` to stderr; `protected_stdin()` reads the protocol from a duplicate of fd 0 and replaces `sys.stdin` by an empty stream. Numpy arrays and Pydantic models are encoded automatically.
- **Server** (`workers/server.py`): handlers are `handler(params: dict, context) -> result`; errors are `WorkerError(code, message, details)`; unexpected exceptions become `internal` errors with the traceback; `context.check()` raises `CancelledError` after a `{"cancel": id}` message; logs are sent as `log` events.
- **Windows pitfall found in the real application**: importing GEMSEO (numpy's DLLs) in a background thread hangs forever while another thread blocks reading the stdin pipe. The worker therefore reports `ready`, imports GEMSEO in the main thread (`gemseo_loaded` / `gemseo_failed`), and only then starts reading requests (they wait in the pipe, about 2 s). GEMSEO has no `__version__`: versions come from `importlib.metadata`.
- Methods are added to the worker by listing modules with a `register(server)` function in `workers/introspection.METHOD_MODULES`; `require_gemseo()` guards methods that need GEMSEO.
- **Client** (`app/worker_client.py`): `QProcess` with `PYTHONPATH` extended by this package's folder (so another interpreter finds it), `request(method, params, callback, timeout)` from any thread (writes are marshalled to the Qt thread), `call(...)` for pool threads only, `cancel(id)`. Deadlines are checked every 50 ms; a timeout or a crash fails the pending requests with `worker_unavailable` and restarts the worker, at most 3 times per minute, then the state stays `crashed` until Tools › Restart worker. Version checks: Python ≥ 3.12, Pydantic 2.x, GEMSEO 6.x, otherwise `incompatible`.
- Page: status bar "Worker: ready — GEMSEO 6.3.3", Tools › Restart worker, and a Tools › Preferences dialog (interpreter, undo steps, stop timeout, concurrent runs); later plans add sections through `preferenceSections`. Changing the interpreter restarts the worker (`PreferencesStore.on_change`).
- **Fix of an issue reported by the user** ("a confirmation window blocks the UI"): the canvas saves its zoom right after startup, which marked a brand-new project as modified, so closing the application asked "Save the changes…?". View-only changes (non-undoable `setLayout`: zoom, expanded containers, port display) are still saved with the project but no longer mark it as modified (`Document.on_content_change`). This supersedes the corresponding sentence of plan 06's notes.
- Client tests use a light fake worker (`tests/python/workers/fake_worker.py`, no GEMSEO) so each test stays well under one second.
